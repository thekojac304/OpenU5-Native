# D-86 (dungeon invalid digit key) -- investigator A, binary-first lens

Report written by a read-only investigation. Nothing in the repository was edited, built or run.
Scratch scripts: `.../scratchpad/dungeon_dis.txt` (full DUNGEON.OVL linear disassembly), `basecheck.py`,
`targets.py`, `callgraph.py`, `callers_banda_fixed.py`, `census_allbases.py`.

Method order: everything in section 2 was disassembled and derived BEFORE any re/notes file or port source was
opened; sections 4-6 were written after.

---------------------------------------------------------------------------------------------------

## 1. Verdict

1. **Binary.** In a dungeon every digit key `'0'..'9'` is routed by DUNGEON.OVL `0x06c4` (arm `0x07bc..0x07d6`)
   to kernel `0x4080` ("Set Active Plr"), and the dispatcher then **forces its own return value to 0**
   (`0x07ce mov [bp-2],ax` immediately overwritten by `0x07d1 mov [bp-2],0`). The kernel's value 1 for an invalid
   member is therefore discarded. Return 0 means the dungeon main loop (`0x0e2e`) skips the whole per-turn block
   `0x0c76` (sleeper wake draws, wanderer move, ambush, tile/trap effects, hunger/poison housekeeping).
   Valid member, `'0'`, digit >= party size, dead member, sleeping member: all five cases are no-turn in the
   dungeon. (The overworld MAINOUT and the town TOWN callers of the same kernel routine do NOT discard the 1: an
   invalid digit costs a turn there. That contrast is the whole point of D-86.)
2. **Digit path draws no RNG** (static call-closure of `0x4080`: 29 kernel routines, none is the RNG `0x2092`, none
   is the clock `0x4f7c`; positive control from `0x4f7c` finds both). It prints only text and redraws the status
   panel.
3. **IMPORTANT nuance the ledger does not state.** The dungeon loop charges the clock **unconditionally** at the top
   of every iteration: `advance_clock(1)` (kernel `0x4f7c`, one call site, DUNGEON `0x0f2f`) runs after EVERY
   command regardless of what the dispatcher returned (Quickness `'Q'` charges every second iteration, Time Stop `'T'`
   none). So "passes no turn" is exactly true for the world turn `0x0c76` but the **1-minute clock tick still
   happens** for a dungeon digit (valid or not). The existing re/notes `dungeon.md` section 1 (#159) already
   derived the unconditional clock call but mislabels `[bp-0xe]` as "the dispatcher's result"; it is the party-state
   byte from kernel `0x39fc`.
4. **Native.** The stray tick arrives because `commands.cpp:781` ends the invalid-member branch with
   `if(!g.position.map.location) r.turn();` and a dungeon session leaves `game.position.map.location == 0`
   (the surface entrance tile) for its whole duration, so `Runner::turn()` (`commands.cpp:199-252`) runs a complete
   **overworld** turn on the surface tile under the dungeon entrance: wind roll, `advance_clock(2)`, hazard roll,
   housekeeping (`turns_since_start++`, hunger, poison), doors, actors, spawn-gate roll and `outdoor_tick`
   (can spawn an overworld monster), Refuge, waterfall. `UiSession::handle_dungeon` and `ui_input_adapter` are NOT
   the source (they only emit `CommandKind::SetActivePlayer`).
5. **TypeScript reference.** Same wrong gate (`game.ts:2187` `this.state.position.location === 0`, true underground)
   but the reference's `runContextTurn` is dungeon-aware (`effectiveLocation`), so the reference only runs
   `tickDoorsAndNpcs()` + `checkRefuge()`: no clock, no RNG, no overworld turn. The reference is therefore
   "accidentally almost right" for D-86 (observable residue: one surface door-timer tick) and still lacks the
   loop-top clock minute.
6. **Smallest routing change that removes only the tick**: add a dungeon discriminator to the one conditional,
   `commands.cpp:781`: `if(!c.dungeon && !g.position.map.location) r.turn();` (and the matching reference gate
   `this.effectiveLocation === 0`). That is "Option A". The binary-exact version ("Option B") additionally charges
   the single loop-top minute (clock only, no housekeeping) for every dungeon digit; see section 7 for the
   trade-off. No existing fixture or test pins a dungeon digit, so Option A changes no corpus.

Confidence: high on the dispatcher/kernel facts and the "no 0x0c76, no RNG" claim; high on the loop-top clock
being unconditional (static, bytes quoted); the only things not proven are listed in section 8.

## 2. Binary facts

### 2.0 Tooling verification (positive controls) and a base-address correction

* Kernel image = `ULTIMA.EXE` after the MZ header (`hdr = 0x80 paragraphs = 0x800`; image 0x86f0 B, entry `cs:0` =
  image `0x81d0`). Offsets below are image offsets (the `--exe` convention).
* **DUNGEON.OVL loads at 0x81d0, NOT 0xE1E0.** The brief's base table and `re/tools/callers_banda.py` (`'DUNGEON.OVL':
  0xe1e0`) are wrong for this file. Evidence:
  * `basecheck.py`: of the 46 distinct negative-rel `E8` targets in DUNGEON.OVL, with `L=0x81d0` **36/36 non-thunk
    targets land on `55 8b ec`** (the other 10 resolve into the kernel thunk table `0x7c02..0x7cb6`, which is
    before `0x81d0` and not a prologue by construction); with `L=0xe1e0`, `0xbfec`, `0xbf80`, `0xa290`, ... **0 hits**.
  * `targets.py` list: `0xffff9680 -> 0x1850` (print string), `0xffff94ea -> 0x16ba` (putchar), `0xffff9ec2 -> 0x2092`
    (rand), `0xffffa730 -> 0x2900`, `0xffffbeb0 -> 0x4080` (digit), `0xffffafa8 -> 0x3178` (generic dispatcher),
    `0xffffb82c -> 0x39fc`, `0xffffcdac -> 0x4f7c` ... all prologues, and the same routines are called by TOWN/MAINOUT
    at the same kernel addresses.
  * Independent: the kernel thunk `0x7a16` is `lcall loader / id 3 / ljmp 0:0x8ffe`; `0x8ffe - 0x81d0 = 0x0e2e` =
    DUNGEON.OVL `dng_main_loop`. Other id-3 thunk targets: `0x9c60-0x81d0=0x1a90`, `0x9db0-0x81d0=0x1be0`,
    `0x9e3a-0x81d0=0x1c6a`, `0x9f1a-0x81d0=0x1d4a`, `0x9fe0-0x81d0=0x1e10`: all function starts in the disassembly.
    (`thunks.py --bases` prints 0x8304 for id 3 because it takes the minimum thunk target, not the load address.)
  * Control reproduced: `callers_banda` with the patched base lists for kernel `0x3178` exactly `DUNGEON 0x07a3,
    MAINOUT 0x0c00, TOWN 0x158f`, matching `re/notes/dungeon-dispatch-gates.md` section 1, and for `0x2900` exactly the
    DUNGEON sites `0x03e5 0x0cd6 0x0e1f 0x1be0` I found by hand.
* Overlay-local call census control: raw-byte scan of DUNGEON.OVL for `E8/E9` -> `0x502` finds `0x076e` (known site).

### 2.1 DUNGEON.OVL key dispatcher `0x06c4` (callers: only `0x0f42`)

```
06c4: push bp / mov bp,sp / sub sp,4 / push si
06cb: mov word ptr [bp-2], 1          ; default return = 1 (turn is charged)
06d0: mov ax,[bp+4]                    ; the key
06d3: cmp ax,0xb / je 0x6f2 ; jle 0x6dd ; jmp 0x7a8
06dd: cmp ax,1 / jge 0x6e5 ; jmp 0x7bc
06e5: cmp ax,4 / jle 0x744 ; cmp ax,5 / je 0x710 ; jmp 0x7bc
...
07a0: push word ptr [bp+4]             ; non-digit, non-special: kernel generic dispatcher
07a3: call 0xffffafa8                  ; -> 0x3178 ; 07a6: jmp 0x771 (mov [bp-2],ax)
07a8: cmp ax,0xd  / je 0x744           ; ENTER   (move)
07ad: cmp ax,0x13 / je 0x776           ; ^S sound toggle
07b2: cmp ax,0x16 / je 0x73a           ; ^V
07b7: cmp ax,0x2e / je 0x744           ; '.'     (move)
07bc: cmp word ptr [bp+4],0x30 / jb 0x7a0     ; below '0'   -> generic
07c2: cmp word ptr [bp+4],0x39 / ja 0x7a0     ; above '9'   -> generic
07c8: ff 76 04          push word ptr [bp+4]
07cb: e8 e2 b6          call 0xffffbeb0        ; -> kernel 0x4080
07ce: 89 46 fe          mov word ptr [bp-2], ax
07d1: c7 46 fe 00 00    mov word ptr [bp-2], 0 ; <<< result discarded, forced 0
07d6: e9 31 ff          jmp 0x70a              ; 070a: mov ax,[bp-2] ; jmp 0x7da (ret 2)
```
Facts: digits are exactly key codes `0x30..0x39` (unsigned `jb`/`ja`, 16-bit compare of the word key). The two moves
are redundant by construction: the second one is the deliberate discard. Return is word 0 for every digit. Other
codes that return the default 1 in this routine include `^S` (`0x0776`..`0x079d` -> `0x70a`) -- not a
digit concern but shows that "forced 0" is a special case, not the norm.

### 2.2 Kernel `0x4080` -- the shared set-active-player routine (3 callers, section 3)

```
4080: push bp / mov bp,sp / sub sp,4 / push si
4087: mov word ptr [bp-2],1            ; default return 1
408c: mov ax,[bp+4] ; 408f: sub ax,0x31 ; 4092: mov [bp-4],ax    ; idx = key - '1' (word)
4095: mov ax,0xa396 ; push ax ; 4099: call 0x1850                 ; print DS 0xa396 = "Set Active Plr:\n"  (ALWAYS)
409c: cmp word ptr [bp+4],0x30 ; 40a0: jne 0x40b8
        40a2: push 0xa3a8 ; call 0x1850                           ; DS 0xa3a8 = "None!\n"
        40a9: mov byte ptr [0x587b],0xff                          ; active char = none
        40ae: call 0x2900                                         ; status-panel redraw
        40b1: mov word ptr [bp-2],0 ; jmp 0x40f7                  ; return 0
40b8: mov al,[0x585b] ; sub ah,ah ; cmp [bp-4],ax ; jae 0x40f0    ; idx >= party_size (UNSIGNED word cmp, byte [0x585b])
40c2: mov si,[bp-4] ; shl si,5                                    ; roster record stride 0x20, base 0x55a8
40c9: cmp byte ptr [si+0x55b3],0x44 ; je 0x40f0                   ; status 'D' (dead)  -> invalid
40d0: cmp byte ptr [si+0x55b3],0x53 ; je 0x40f0                   ; status 'S' (asleep)-> invalid
40d7: mov al,[bp-4] ; mov [0x587b],al                             ; active char = idx
40dd: mov ax,si ; add ax,0x55a8 ; push ax ; 40e3: call 0x1850     ; print the record's name string (rec+0)
40e6: push 0xa ; 40ea: call 0x16ba                                ; putchar('\n')
40ed: jmp 0x40ae                                                  ; call 0x2900 ; [bp-2]=0 ; return 0
40f0: push 0xa3b0 ; call 0x1850                                   ; DS 0xa3b0 = "Invalid!\n"
40f7: mov ax,[bp-2] ... ret 2                                     ; returns 1 (the default) for every invalid case
```
Strings (DATA.OVL file offset = DS + 0x10, read in this session): `0xa396 "Set Active Plr:\n"`,
`0xa3a8 "None!\n"`, `0xa3b0 "Invalid!\n"`. Status bytes: `'D'=0x44`, `'S'=0x53`; every other status (`'G'`, `'P'`, ...)
is valid. The party-size test is `[0x585b]` (byte), not the roster count: a companion at an inn (roster idx >=
party size) is invalid.

Outcome table in the DUNGEON (kernel return -> dungeon return):

| key | member state | text printed | `[0x587b]` | `0x2900` redraw | kernel ret | **dungeon ret** |
|---|---|---|---|---|---|---|
| `'0'` | any | "Set Active Plr:\n" "None!\n" | `0xff` | yes | 0 | **0** |
| `'1'..'9'`, idx >= `[0x585b]` | none | "Set Active Plr:\n" "Invalid!\n" | unchanged | no | **1** | **0** |
| digit, idx < party size, status `'D'` | dead | same as above (Invalid) | unchanged | no | 1 | **0** |
| digit, idx < party size, status `'S'` | asleep | same as above (Invalid) | unchanged | no | 1 | **0** |
| digit, idx < party size, other status (`G`,`P`,...) | valid | "Set Active Plr:\n" `<name>` `\n` | `idx` | yes | 0 | **0** |

`'7'..'9'` are not special: with party size <= 6 they are simply idx >= party size. Digit `'0'` is tested before any
party logic. No path of the routine reads the RNG, the clock or the turn counter (call-closure below).

Call-closure proof (`callgraph.py 4080`): routines reachable: `0x1850 0x16ba 0x17f4 0x1a3e 0x1b94 0x1bf2 0x1cca 0x1cee
0x1f12 0x1f26 0x1f77 0x216c 0x2726 0x2884 0x2900 0x4c2a 0x4cce 0x4f3c 0x0a70 0x0aa6 0x0b10 0x0b2d ...` (29). Neither
`0x2092` (rand: `55 8b ec 56 57 1e a1 20 54 ...`, state `[0x5420]`, one state update per call) nor `0x4f7c` (clock) is
in it; the positive control starting from `0x4f7c` does reach `0x2092`, `0x3f36`, `0x2900`. The display driver
is reached only through `lcall [0x5350]` (indirect, not followed); it is the graphics/text driver, not game logic.

### 2.3 Dungeon main loop `0x0e2e` (only caller: ULTIMA.EXE `0x010e`, `push [bp-2] ; call 0x7a16`)

Setup `0x0e2e..0x0f15` then falls into the loop. Locals: `[bp-0xc]` = "keep running" flag (init 1), `[bp-0xe]` =
party-state result (init 0), `[bp-4]`/`di` = "world advances" toggle, `si` = dispatcher result.

Key read + dispatch (every iteration):
```
0f36: call 0x3d6                    ; read a key (loops internally until non-zero; prints '\n' + prompt first)
0f39: mov [bp-8],ax
0f3c: cmp ax,0xffff ; jle 0xf47     ; (never taken: 0x3d6 returns a positive key)
0f41: push ax
0f42: call 0x6c4                    ; the dispatcher of 2.1
0f45: mov si,ax                     ; si = dispatcher result (0 for a digit)
0f47: cmp byte [0x5893],0x21 ; jae 0xf53       ; underground: continue
0f53..0f78: read the cell under the party into [bp-2]/[bp-6]
0f7b: or si,si
0f7d: je 0xf87                      ; si == 0 -> SKIP the world turn
0f7f: mov al,[bp-2] ; push ax ; push di
0f84: call 0xc76                    ; world turn (only caller of 0x0c76)
0f87: cmp byte [0x5893],0x21 ; jae 0xf93       ; underground: -> loop top
```
Loop top (runs after EVERY command, `si` is not consulted again; `0x0fa5 mov si,1` overwrites it):
```
0f93: cmp word [bp-0xc],0 ; je 0xff2                 ; flag cleared -> leave
0f99: cmp byte [0x5893],0x20 ; jbe 0xff2             ; not underground -> leave
0fa0: mov [bp-0xc],1 ; 0fa5: mov si,1
0fa8: call 0xffffb82c                                 ; kernel 0x39fc party_state: 0 = a 'G'/'P' member, 1 = only 'S', -1 = none
0fab: mov [bp-0xe],ax
0fae: cmp ax,si ; jne 0xfc3 ; (r==1: putchar('\n'), call 0x4c2a, print DS 0x2ddd "Zzzzzz...\n")
0fc3: cmp [bp-0xe],0 ; jge 0xfd0 ; mov [bp-0xc],0 ; sub si,si     ; r<0: leave after this
0fd0: cmp [bp-0xe],0 ; jne 0xf93                      ; r != 0 -> back to the loop top (no key, no clock)
0fd6: cmp byte [0x587a],0x54 ('T') ; jne 0xfe0 ; jmp 0xf1e
0fe0: cmp byte [0x587a],0x51 ('Q') ; jne 0xfea ; jmp 0xf1e
0fea: mov di,1 ; 0fed: mov ax,di ; 0fef: e9 3c ff  jmp 0xf2e          ; 0xff2-0xc4 = 0xf2e
0f2e: push ax                                         ; arg 1
0f2f: call 0xffffcdac                                 ; kernel 0x4f7c = advance_clock(1)
0f32: jmp 0xf36                                       ; next key
0f1e: cmp byte [0x587a],0x51 ; jne 0xf34 ; xor di,1 ; je 0xf36 ; push 1 ; call 0x4f7c ; jmp 0xf36   ; 'Q': tick every 2nd pass
0f34: sub di,di ; (falls to 0xf36)                    ; 'T': no tick, di = 0
```
So per iteration, ignoring the exceptional `[bp-0xe]` values: `advance_clock(1)` -> key -> dispatch -> (`0xc76` iff
`si != 0`). **`si` gates only `0x0c76`.** `0xf2f` is the **only** `advance_clock` call in DUNGEON.OVL
(`census_allbases.py 4f7c` style scan; callers_banda: `DUNGEON.OVL 0x0f2f` only; the other callers are
`ULTIMA.EXE 0x3cfc/0x6356`, `TOWN 0x0511/0x1328/0x15d4`, `MAINOUT 0x0006/0x0066/0x0462/0x068c/0x0a56/0x0c3d`,
`CMDS 0x0318/0x064b`). Contrast: TOWN `0x15b6 cmp [bp-0xa],0 ; jne 0x15bf ; jmp 0x1686` and MAINOUT `0x0c30 cmp [bp-8],0
; jne 0xc39 ; jmp 0xd14` charge their clock (`push 1 / push 2 ; call 0xcdac`) ONLY when the command returned non-zero.
The dungeon loop has no such gate.

Kernel `0x4f7c advance_clock(n)` (read in full, `0x4f7c..0x519c`): `[0x5880]=[0x587f]` (prev hour); if `[0x587a]=='Q'`
`n>>=1` (min 1); if `[0x587a]!='T'`: `[0x5881] += n` (minutes) and saturating `-n` on `[0x58a7]` and `[0x58a6]` via
`0x3f36`; minutes `> 0x3b` -> `-0x3c`, `0x3f36(1,&[0x588c])`, `[0x587f]++` (hour); hour `> 0x17` -> day rollover with the
Shadowlord relocation loop that calls `rand(1,8)` (`0x500c`) and the calendar. **RNG draws of a plain minute tick: 0.**
Draws happen only when the tick crosses midnight.

World turn `0x0c76(di, tile)` (skipped when `si == 0`; the body of what a digit does NOT run): per roster member with
status `'S'` (`0x0ca3 cmp byte [si],0x53`) one `rand(0,0x3f)` (`0x0caa push 0 ; 0x0cab push 0x3f ; call 0x2092`),
`< 4` -> status `'G'` (`0x0cb7 mov byte [si],0x47`); `if di != 0 call 0x07e2` (wanderer step: up to 8 attempts,
`rand(0,3)` per attempt, `rand(0,7)` gate when it would hit the party) and `0x0b7e` (ambush text); then the tile
dispatch (`0x0d17..0x0e1f`: fields, rooms, traps) ending in `0x0e1f call 0xa730 (0x2900)` and `0x0e22 call 0xa918 (0x2ae8
housekeeping: hunger/poison)`. None of that runs for a digit.

### 2.4 Answers to the specific questions

* What a VALID digit does: sets `[0x587b]` (active player, rec index), prints "Set Active Plr:\n<name>\n", redraws the
  status line (`0x2900`: `F:`/`G:`/time/food etc. panel), **no prompt, no status page, no turn (world turn skipped)**.
  The dungeon clock still advances by the loop-top minute afterwards (2.3).
* Invalid member: prints "Set Active Plr:\n" then "Invalid!\n", **no redraw**, state unchanged, dungeon returns 0.
* Clock: **+1 minute at the next loop top (same as every other dungeon command)**; world-turn counters/housekeeping:
  not run. Turn counter in the sense of "monsters/housekeeping step": not advanced.
* RNG: **0 draws** from the dispatcher+kernel path; 0 from the minute tick except on a midnight crossing. (Separate,
  already-declared: the idle key-wait loop redraws the 3D view with 2x`rand(0,100)` per frame (`0x111e`),
  time-driven; `re/notes/dungeon.md` section 3 declares it out of scope.)
* Output: exactly the strings above (kernel prints them; the UI echo `Set Active Plr:` in `handle_dungeon` mirrors
  `0xa396`).
* digit `0`: "None!", `[0x587b]=0xff`, redraw. Digits beyond party size, dead, asleep: "Invalid!" (no redraw).

## 3. Callers census

Method: `callers_banda.py` (patched copy with `DUNGEON.OVL: 0x81d0`) and `census_allbases.py` (every overlay file tried
against every candidate base, plus ULTIMA.EXE at base 0), E8/E9 rel16, over-reporting, never missing. Positive
controls: `0x3178`, `0x2900`, `0x502` as in 2.0.

| routine | callers (all) | relevant? |
|---|---|---|
| kernel `0x4080` set-active-player | `DUNGEON.OVL 0x07cb` (rel `0xbeb0`), `MAINOUT.OVL 0x0c0c` (rel `0xbeb0`), `TOWN.OVL 0x0ef3` (rel `0xbeb0`); no other overlay under any base, none in ULTIMA.EXE | DUNGEON = the D-86 site; MAINOUT/TOWN are the contrast |
| DUNGEON `0x06c4` dispatcher | `0x0f42` only | yes |
| DUNGEON `0x0c76` world turn | `0x0f84` only | yes (skipped for a digit) |
| DUNGEON `0x0e2e` main loop | thunk `0x7a16` <- `ULTIMA.EXE 0x010e` only | context |
| DUNGEON `0x03d6` key read | `0x0f36` only | context |
| kernel `0x4f7c` advance_clock | see 2.3: DUNGEON `0x0f2f` + 12 other sites | DUNGEON `0x0f2f` = the loop-top minute |
| kernel `0x3178` generic dispatcher | `DUNGEON 0x07a3`, `MAINOUT 0x0c00`, `TOWN 0x158f` | non-digit keys |
| kernel `0x39fc` party state | `TOWN 0x126b 0x12c0 0x1436 0x15bf`, `MAINOUT 0x0aa2 0x1158 0x1b4b`, `CMDS 0x1bfd`, `DUNGEON 0x0d32 0x0fa8` | `0x0fa8` is the loop-top check |

How each of the three `0x4080` callers treats the return value (disassembled):

* **DUNGEON** `0x07cb..0x07d1`: discarded, forced 0 -> no `0x0c76`, clock still +1 at the loop top.
* **MAINOUT** `0x0c06..0x0c39`: `call 0xffffbeb0 ; 0x0c0f mov [bp-8],ax` ... `0x0c30 cmp [bp-8],0 ; jne 0xc39 ;
  0xc39 push 2 ; call 0xcdac (advance_clock(2))` -> an invalid digit on the overworld costs the full overworld turn
  (the native `r.turn()` models exactly this arm).
* **TOWN** `0x0e34` (digit/harpsichord entry, `[bp-2]=3` = "re-read key" while seated at the instrument): not seated
  -> `0x0ef0 push [bp+4] ; call 0xffffbeb0 ; 0x0ef6 mov [bp-2],ax` returned to the loop (`0x159a mov [bp-0xa],ax ; 0x15b6
  cmp [bp-0xa],0 ; jne 0x15bf`) -> invalid digit = **a 1-minute town turn** (`0x15d4 push 1 ; call advance_clock`).
  Both ports print without a turn in a town (adjacent, bounded divergence; see section 8).

## 4. Reference (TypeScript) status

* `game/src/core/game.ts:2174-2200` `setActivePlayer(digit)`; invalid branch `2184-2191`:
  `events.push({kind:"message", text:"Invalid!"}); if (this.state.position.location === 0) { events.push(...this.runContextTurn({ consumed: true })); }`.
  The gate tests the **stored** location, which is 0 underground (`enterDungeon` keeps `state.position` on the surface
  entrance tile on purpose; `game.ts:4782-4815` `effectiveLocation` docblock says exactly this). So the branch runs.
* `runContextTurn` (`game.ts:2401-2655`) reads `effectiveLocation` (`2408`; `0x21..0x28` underground) so it takes the
  dungeon tail `2651-2654`: `tickDoorsAndNpcs(); events.push(...checkRefuge());` -- **no clock, no RNG, no housekeeping,
  no overworld turn.** Residue: one surface door-timer tick (`tickDoors` 2861: `doors?.tick()` and re-serialises
  `state.openDoors`), `tickNpcs` (no-op at location 0), `checkRefuge` (harmless: the original runs the same death check
  every loop top).
* Call sites: dungeon digits `game/src/main.ts:1617-1631` (`hud.echo(CMD_STRINGS.setActive); game.setActivePlayer(Number(ev.key))`;
  the comment at 1612-1616 already says "retorno FORZADO a 0 (@0x07d1) = SIN turno"); overworld/town `main.ts:5908-5913`.
* Doc comment `game.ts:2166-2170` says town/dungeon print "sin turno (no derivado)". This investigation derives the town
  (1-min turn) and the dungeon (world turn skipped, clock minute still charged); the comment is stale.
* Dungeon clock model elsewhere in TS: `MINUTES_PER_ACTION_DUNGEON = 1` (`world/survival.ts:111`), charged by
  `dungeon-cmds.ts:326,410,437` and `game.ts:2945` (`ignite`), `3084` (`gemViewTurn`) through `advanceTurn` (clock +
  housekeeping). A digit never reaches any of them.
* Verdict: no overworld turn, no divergence in RNG. Divergences: (a) wrong gate (`position.location` instead of

## 7. Proposed fix and boundary test cases

### 7.1 Option A -- minimal, removes only the tick (what the ledger asks)

* Native: `commands.cpp:781` -> `if(!c.dungeon && !g.position.map.location) r.turn();` (`c.dungeon` is the flag
  `Ignite`/`ViewGem` already use at 785-791). Nothing else in the 774-784 arm changes. The overworld (`location==0`,
  `!c.dungeon`) keeps its turn; towns keep none.
* Reference: `game.ts:2187` -> gate on `this.effectiveLocation === 0` (or `!this.dungeonState`), removing the door-timer
  residue; update the stale docblock 2166-2170 and `main.ts:1612-1616` already describes the intended behaviour.
* Why this is "routing only": the discriminator is the existing `c.dungeon`, the arm structure is kept.

### 7.2 Option B -- binary-exact (decide before implementing)

The binary additionally charges `advance_clock(1)` after the digit (loop top, 2.3), with **no** housekeeping, **no** world
turn: native `else if(c.dungeon) advance_clock(g, c.turn, 1, &r.rand, c.sky);` (same call shape as `commands.cpp:220`),
reference `advanceClock(this.state, 1, this.rand, this.skyRefreshCtx)` (as `game.ts:2440`). Apply to every dungeon digit
(valid, `'0'`, invalid) to be exact. Caveats the implementer must weigh: (1) the same unconditional loop-top minute
applies to every other free dungeon command (Z-stats, Look, Attack, turning, ...), which native/TS currently charge
inconsistently (`DungeonCommand` charges clock+housekeeping for everything but Attack; the non-`DungeonCommand` free
commands charge nothing); fixing only digits would be an island. (2) Native's `advance_turn` bundles housekeeping the
binary gates on `si != 0`; Option B for digits must use `advance_clock` alone. (3) The minute is cross-fixture visible
(light/torch timers, hour boundary). Recommendation: do Option A for D-86 and record a separate ledger row for the
loop-top-clock class (binary-proven here), unless the parity batch wants the whole class.

### 7.3 Boundary test cases (use a dungeon scenario: `dungeon.active`, `c.dungeon=true`, position map location 0)

Party fixtures: size 3 `[G, P, G]`, plus variants with member 2 = `'D'`, `'S'`; party size 6; Underworld-origin
(`position.map.floor=255`) variant (it also makes the `rand(0,255)` hazard draw visible).
Assertions per case: messages, `active_character`, `time` (minute, hour), `turns_since_start`, RNG seed, food, party HP,

   model (`torch_turns`, `light_spell_minutes`), not proven here; irrelevant to D-86's gate.

   asleep, prints "Zzzzzz...\n" each pass): read literally it never exits unless something else changes the roster. I did
   not chase it (out of scope); it does not affect the digit path but is a candidate odd corner (a real game state or a
