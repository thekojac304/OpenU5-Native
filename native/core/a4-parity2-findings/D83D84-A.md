## 1. Verdict

1. There is exactly ONE resurrection routine in the original: **CAST2.OVL file offset 0x05e0** (Pascal convention, `ret 4`, two word args pushed left to right: `member`, `mode`). It is reached through the kernel thunk **ULTIMA.EXE CS:0x7ef6** (`9a ec 02 2e 07 | 12 00 | ea c0 e7 00 00`: overlay id 0x12 = 18 = CAST2, entry offset 0xe7c0, CAST2 band base 0xe1e0 -> file offset 0x05e0; the bytes at 0x05e0 are `55 8b ec 83 ec 08 56`, a prologue).
2. It has **exactly four callers** (exhaustive census, section 3): CAST.OVL 0x10f3 (spell 42 In Mani Corp, mode 0), CAST.OVL 0x12ee (scroll 6 In Mani Corp, mode 1), SHOPPES.OVL 0x16f5 (healer Resurrect, mode 0xff), BLCKTHRN.OVL 0x0b95 (Refuge loop, mode 0xff). The original callers listed in the brief are correct and complete.
3. **The working hypothesis in the brief is half wrong, and the ledger is right.** The healer and the Refuge DO call the shared routine; the port divergence (D-83, D-84) is that both ports skip it. The text "the healer sets HP 1" (ALPHA4_UI.md 14.5) describes the PORTS' healer, not the binary: in the binary the routine sets HP 1 internally and the healer (and the Refuge) then overwrite HP with the RECOMPUTED maximum (`mov ax,[si+0x55ba] / mov [si+0x55b8],ax` after the call). The ledger text for D-83/D-84 (ALPHA2_PRESERVATION_LEDGER.md rows D-83, D-84) matches what I derived, including "with the karma the party died with, before the floor of 75".
4. The routine (full semantics, all verified by executing the real bytes): if the member is not status 'D' it changes nothing (prints DS 0x953c "Not dead!\n" only when mode != 0) and returns 0; if the member index is negative it returns -1 silently; otherwise it sets status 'G', HP 1, MP by class (A/M = INT, B = INT>>1, anything else untouched), then **if karma (byte, unsigned) < 0x62 (98): XP = low16( (long)XP * karma / 100 )** (signed 32-bit multiply and divide, truncation toward zero), then **level = 1 + bitlength(XP/100)** (loop, no table, no cap), **maxHP = 30 * level**, plays a ceremony only in modes 0 (effect 8) and 1 (effect 6), sets DS:0xa9fa = 1, returns 1. No RNG draw. Karma is never written.
5. Per-path result after the routine: spell and scroll leave HP = 1; healer and Refuge set HP = new maxHP (30 * level) afterwards. At the Refuge the karma used for the cut is the karma at death (the floor of 75 is applied at 0x0bfd, AFTER the revive loop 0x0b54-0x0bb3).
6. Both ports already contain a byte-exact copy of the routine for the spell and scroll (`applyResurrect` in game/src/core/magic/cast.ts:545, `apply_target_spell` Resurrect in native/core/src/magic.cpp:231). The divergences are only the two skipping call sites: TS `healerHeal` (game/src/core/shops/shops.ts:1238-1241) and TS `partyRefuge` (game/src/core/world/blackthorn.ts:535-543); native `healer_heal` (native/core/src/shops.cpp:226-230) and native `resolve_refuge` (native/core/src/quest_world.cpp:189).
7. Tooling warning (affects every "exhaustive caller" claim): the overlay base table in the task brief is WRONG for BLCKTHRN (it says 0xE63E, true 0xA290), COMBAT (0xBFEC, true 0xA290), CAST (0xA8D8, true 0xBF80), DUNGEON (0xE1E0, true 0x81D0), COMSUBS (0x85FE, true 0xE1E0), SHOPPES3 (0xA5F6, true 0xE1E0), LOOKOBJ (0xA444, true 0xA290), DNGLOOK (0xA2B6, true 0xA290), OUTSUBS (0x81D0, true 0xA290) and INTRO (0xCD3A, true 0x81C0); it already corrects TALK (0xBF80) and CAST2 (0xE1E0). The `BASES` dict inside `re/tools/callers_banda.py` is wrong for 15 overlays (OUTSUBS, COMSUBS, TALK, SHOPPES2, SHOPPES3, LOOKOBJ, DNGLOOK, CAST, COMBAT, DUNGEON, BLCKTHRN, CAST2, ENDGAME, FLAMES, INTRO) and omits ZSTATS and FONT. The stock tool run on 0x7ef6 returns ONE hit (SHOPPES 0x16f5) and silently misses the Refuge (BLCKTHRN 0x0b95) and both CAST callers. Correct bases are in section 2.F0 (they agree with re/notes/overlay-load-layout.md section 1, which I read only after fitting them myself).

Confidence: high for the routine, the four callers and the per-path sequences; medium-high for "no other transitive RNG/side effect" (the callee `effect(n)` and the kernel print were not traced to the bottom).

## 2. Binary facts

### F0. Overlay call bases (positive control, derived first)

Method: for every overlay file, take every `E8 rel16` whose target `(i+3+rel) & 0xffff` lies outside the file, add a candidate base, and score how many land on a kernel function prologue (`55 8b ec`) or a loader thunk (`9a ec 02`) in ULTIMA.EXE (image = raw file minus the 0x800-byte MZ header, so kernel CS offset = raw - 0x800). Best bases (hits/calls): SHOPPES 0xa290 (228/233), BLCKTHRN 0xa290 (132/142), COMBAT 0xa290 (160/170), NPC/LOOKOBJ/DNGLOOK/OUTSUBS/ENDGAME 0xa290, CAST 0xbf80 (270/283), TALK/CMDS/SJOG 0xbf80, CAST2 0xe1e0 (186/197), COMSUBS/ZSTATS/SHOPPES2/SHOPPES3 0xe1e0, TOWN/MAINOUT/DUNGEON 0x81d0, INTRO 0x81c0 (552/563). The overlay-id to file mapping: thunk id = 1-based index into the name table at ULTIMA.EXE image 0x8113 (TOWN, MAINOUT, DUNGEON, INTRO, FLAMES, NPC, COMBAT, BLCKTHRN, LOOKOBJ, DNGLOOK, OUTSUBS, SHOPPES, ENDGAME, SJOG, CMDS, CAST, TALK, CAST2, ZSTATS, COMSUBS, SHOPPES2, SHOPPES3, FONT, DATA); verified by testing each id's thunk targets against the prologues of the candidate file at its fitted base (e.g. id 18: 15/16 of its thunk targets at base 0xe1e0 are `55 8b ec` in CAST2.OVL; id 8 BLCKTHRN, id 12 SHOPPES 9/11, id 16 CAST).
The thunk table's own "minimum target per id" (what `thunks.py --bases` prints and what the brief's table and callers_banda.py reuse: BLCKTHRN 0xe63e, COMBAT 0xbfec, CAST 0xa8d8, CAST2 0xc29e, SHOPPES3 0xa5f6, COMSUBS 0x85fe, ...) is the address of the FIRST ENTRY of that overlay (and for some ids simply another overlay's group), not its load base. Overlays live in 5 nested bands (0x81d0 / 0xa290 / 0xbf80 / 0xe1e0 / DATA 0xf630) and the near-call base is the band base.
Positive controls that the fitted bases are right: (a) four overlays in three different bands all resolve their redraw call to the SAME kernel prologue: SHOPPES `call 0x8670` (0x1707), BLCKTHRN `call 0x8670`-equivalent (0x0b9f), CAST `call 0x6980` (0x10f9, 0x12f4) -> kernel 0x2900; (b) SHOPPES 0x16c3 `call 0x75c0`, CAST `call 0x58d0`, CAST2 `call 0x3670` -> kernel 0x1850 (print_string, prologue `55 8b ec 83 ec 42`); (c) SHOPPES 0x01ad/0x01c5 `call 0x7e02` -> kernel 0x2092, whose body is the LCG `add ax,0x9248 / ror x3 / xor ax,0x9248 / add ax,0x11` over DS:0x5420 with `and ax,0x7fff` and `div` by `hi-lo+1`: the RNG (lo pushed first, hi second).

### F2. The routine, CAST2.OVL 0x05e0-0x06e8 (offsets are file offsets; band base 0xe1e0)

Calling convention: Pascal, callee cleans (`ret 4`). Stack: `[bp+6]` = member (first pushed), `[bp+4]` = mode (second pushed). Local `[bp-2]` = record pointer, `[bp-4]` = scratch quotient, `[bp-6]` = return value, `[bp-8]` = level counter.
Character record: 32 bytes at DS:0x55a8 + 0x20*member; +0x0a class byte, +0x0b status byte, +0x0e INT, +0x0f MP, +0x10 HP (word), +0x12 maxHP (word), +0x14 XP (word), +0x16 level (byte). (Confirmed against INIT.GAM: all 16 records satisfy level = 1 + bitlen(XP/100) and maxHP = 30 * level, and 15 of 16 satisfy the MP rule; the 16th is the Avatar template placeholder.) DS:0x5888 = karma byte (INIT.GAM file 0x2e2 = 75), DS:0x585b = party size, DS:0x57aa = gold word.

Calls inside: kernel 0x1850 print_string (only "Not dead!"), kernel 0x0442 lmul, kernel 0x0496 ldiv, CAST2 0x0000 effect(n). No call to the RNG (kernel 0x2092); effect(n) (CAST2 0x0000-0x009a) only calls kernel 0x223c, 0x0a70, 0x0b86 and 0x2192 (PC speaker tone sweep, `out 0x42/0x61`, DS:0xa9ce = sound flag) and the census shows no rand call inside CAST2 at all and none in kernel 0x0000-0x2800. Karma (DS:0x5888) is never written; DS:0xa9fa = 1 only on success. DS:0xa9fa semantics: TOWN 0x0dd3, MAINOUT 0x05a3 and DUNGEON 0x03de test it, call `0xa730` (= kernel 0x2900, the same redraw all four callers also call), then clear it. It is a redraw flag, not a clock tick.

Arithmetic details an implementer needs:
* XP sign: `cwd` after `mov ax,[bx+0x14]` sign-extends; for XP < 0x8000 (the whole game range, XP <= 9999) there is no difference from unsigned. For XP >= 0x8000 the routine sees a negative number (level 1, maxHP 30, XP unchanged when karma >= 98). Not reachable in play.
* Karma: byte, zero-extended, compared unsigned (`jae`): karma 0..97 cut, 98..255 no cut. So karma 98 and 99 (and any 100) get NO cut; the cut at karma 97 is 3 percent.
* XP' = floor(XP * karma / 100) (non-negative operands, so floor == trunc), computed in 32 bits, then only the low 16 bits are stored (no overflow possible for XP <= 9999, karma <= 97).
* Level: `q = XP'/100` (signed 16/16 `idiv`, truncation). Level = 1 + number of loop iterations = 1 + bitlen(q): q = 0 -> 1; 1 -> 2; 2-3 -> 3; 4-7 -> 4; 8-15 -> 5; 16-31 -> 6; 32-63 -> 7; 64-127 -> 8; 128-255 -> 9; 256-327 -> 10 (XP <= 32767). XP thresholds: 100, 200, 400, 800, 1600, 3200, 6400, 12800, 25600. There is NO cap at 8 and no table; the in-game XP ceiling (9999) keeps it <= 8.
* maxHP = 30 * level, 16-bit (`imul dx`, low word stored). It REPLACES the old maxHP (up or down). HP is set to 1 first (before MP/XP/level).
* MP: class byte 'A' (0x41) or 'M' (0x4d): MP = INT (record +0x0e, byte). 'B' (0x42): MP = INT >> 1 (word shr then low byte). Any other class byte (e.g. 'F'): MP untouched (not zeroed). maxMP is not stored anywhere (it is INT).
* Order of mutation: status G, HP 1, MP, [XP], level, maxHP, ceremony, return 1, DS:0xa9fa = 1.

Members revived: indices 0 .. party_size-1 (the party, NOT the roster; `[0x585b]` is re-read each pass). The routine is called for EVERY one of them; for a member that is not 'D' it would print "Not dead!\n" (mode 0xff != 0), change nothing, and the caller would still set HP = maxHP. This cannot happen in practice: party_refuge is only entered when kernel 0x39fc (party state) returns -1, i.e. NO member within party_size has status 'G' (0x47) or 'P' (0x50) and none is 'S' (0x53) (0x3a28-0x3a47; -1 at 0x3a6a), so every member is 'D'. The karma seen by the routine is the karma at death; the karma speech index (karma/20, 0x0b03) also uses the death karma. Refuge reached from: MAINOUT 0x0af0 and DUNGEON 0x1014 through the kernel wrapper 0x0e7c (`call 0xe26 / call 0x7a5e / call 0xe1d`), and TOWN 0x1865 directly through thunk 0x7a5e (MAINOUT tests `cmp [bp-6],-1` at 0x0ac2 after `call 0xffffb82c` = kernel 0x39fc).
