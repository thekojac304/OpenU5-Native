# D-85 (lens B, ports first) -- the location-29 (Stonegate) trapdoor

Investigator: ports-first pass, then independent binary derivation. Read-only: nothing in the repo
was edited, no build or ctest was run. Scratch scripts: `findings/d85b/reach.py`, `findings/d85b/census2.py`.

Evidence grades used below:
- BINARY = I disassembled it in this session (re/tools/dis16.py, capstone 16-bit) and quote the instructions.
- NOTE/PORT = read from a re/notes file or from game/ or native/ source; secondary, not proof.

---------------------------------------------------------------------------------------------------

## 1. Verdict

1. **D-85 as recorded is CONFIRMED by the binary.** The TPK tail of the Stonegate trapdoor loops over
   `[0x585b]` (the byte `g_party_size`), never over the roster. Loop `TOWN.OVL 0x0ff9-0x103a`
   touches roster slots `0 .. party_size-1` only, setting HP (word) = 0 and status = 'D' (0x44).
   Slots `>= party_size` (inn companions) are not touched. Both ports kill the whole roster
   (native `quest_world.cpp:234` over `character_count`; reference `game.ts:2720` over `state.characters`).
2. **NEW, larger finding the ledger does not list: the trapdoor branch has a prologue both ports omit.**
   Between the "A TRAPDOOR!" print and the Stonegate test (`0x0f96`) the original runs
   `[0x587c]=0 ; call 0x5910 (viewport redraw + wind tick) ; call 0x2aa8 (party damage, rand(1,8) per living member)`
   (TOWN `0x0f7e-0x0f93`). So **every trapdoor, in every location, makes one wind roll and then
   deals 1..8 damage to each living party member (<= 6 slots, < party_size), before either the
   TPK or the one-floor fall.** Both ports comment "no RNG anywhere in the branch"
   (`game.ts:2672`, `turn.ts:~547`); the binary says otherwise. This changes the RNG stream
   and the Stonegate draw order, so the implementer of D-85 must decide on it (see 7). The
   TPK tail itself (`0x0fa0-0x1037`) has no game-RNG draw.
3. The trigger is exactly tile `0x8c` under the party on a small map, and location 29 = Stonegate, whose
   only floor (z=0) has tile 0x8c on the 8-cell ring around (15,15): (14..16, 14..16) minus (15,15).
4. Nothing in the native corpora, the turn fixtures or the TS suite pins the roster-wide kill with a
   roster larger than the party (see 6). Changing the kill bound alone changes **no fixture**; adding the
   prologue (finding 2) changes `fixtures/turns.json` and needs `generate-turn-fixtures.ts` regeneration.
5. Two small satellite divergences surfaced (7.4 audio burst count uses `character_count`; 7.5 the active-member
   clear in housekeeping).

Confidence: high for the loop bound, indices, results, text, trigger, caller census; high for the prologue
(instructions quoted, callees identified); medium for exact wall-clock timings (calibration data not derived).

### 2.3 RNG order (turn with a trapdoor under the party)

1. Wake loop: one `rand(0,15)` per 'S' member among slots < party_size, in index order (as today in both ports).
2. Prologue: one wind tick through `0x5910`, then `0x2aa8`'s `rand(1,8)` per living member (2.4, 2.5).
3. Fall: loop rescans (each lap repeats 2). TPK: nothing more.
4. `0x2ae8` housekeeping: unchanged (dead members consume nothing).

### 2.4 `0x5910` (viewport redraw) -- the wind tick, shared with the Burning path

`5918 mov [0x545e],0xff`; `591d cmp [0x587a],0x54 ('T' time stop) ; jne ; 5924 mov [0x5891],0`; `5929 cmp [0x58a4],0 ; jne 5933 ; jmp 5a1d`;
`5933 cmp [0x5891],0 ; je 5954` (latch 0: skip wind + actor animation); else `call 0x4552` (unless latch == 0xff), `call 0x2f62` = wind roll
(`rand(0,63)`; if 0: `rand(0,4)` into si, and when si == 0 `rand(0,255) >= 0xc0` accepts else re-roll; then `0x2e96(si)`), `0x475a`, `0x70a6`; `5a1d mov [0x5891],1`.
`0x4552` and `0x5394 -> 0x51a0` also reach a rand call (actor animation / ambient), which both ports already treat as outside the
modelled "wind" stream (wind-rand-decision.md). The trapdoor reuses exactly the routine the Burning path calls at `0x10ba`, so whatever
the ports model for `0x10ba` is what `0x0f8a` needs. Caveat inherited by every `0x5910` site: the ports guard only on `time_spell != 'T'`;
the real gate also has `[0x58a4]` and the latch `[0x5891]` (unmodelled residue, defectos-d3d6d7-acta.md).

### 2.5 `0x2aa8` (party damage) and `0x2a52`

```
2ab0  sub si,si ; mov di,0x55b3
2ab5  mov ax,si ; mov cl,[0x585b] ; sub ch,ch ; cmp ax,cx ; jae 0x2ad6   ; slot >= party_size: skip
2ac1  cmp byte [di],0x44 ; je 0x2ad6                                       ; only 'D' is skipped ('S','P','G' all hurt)
2ac6  push si ; push 1 ; push 8 ; call 0x2092 ; push ax ; call 0x2a52     ; rand(1,8), then damage(si, amount)
2ad6  add di,0x20 ; inc si ; cmp si,6 ; jl 0x2ab5                          ; always 6 iterations, no early exit
```
`0x2a52(idx, amt)`: `0x2a28(idx)` flash, noise burst `0x223c(0x7d0,0x640,0xa)`, `0x2a28(idx)`, `HP -= amt` (word), `if (signed) HP <= 0`: HP=0, status 'D',
and if `[0x587b] == idx` then `[0x587b]=0xff`; then `0x2900`. No game RNG inside. **Kernel `0x2aa8` is the same routine the notes call
party_random_damage.** The ports' `party_random_damage` (native `turn.cpp:71`, reference `survival.ts:408`) is faithful to it
(bound `party_size && i<6`, skip 'D', one `rand(1,8)` per living member).

### 2.6 Other facts worth carrying

- Live actor table `DS:0x5c5a`: 32 records x 8 bytes (record 0 is the party's own: x,y,floor are rewritten there at `TOWN 0x160d-0x161c`). The TPK
  zeroes all 0x100 bytes; both ports instead erase persisted interior objects for (location,floor) (native `quest_trapdoor` lines 233; reference
  `stonegateLavaWipe` filter). Live townspeople are not modelled by either; harmless today because the Refuge relocates immediately, but see 8.
- `[0x587b]` is the active character (cmds.md:477). The housekeeping `0x2ae8` loop `0x2b14-0x2b25` clears it when that member is 'D'
  (`cmp ax,0x44 ; ... cmp di,[0x587b] ; jne ; mov byte [0x587b],0xff`). The TPK itself writes status directly and never clears it, so the
  original clears it one instruction later in the same turn.
