## 1 Verdict

The ledger entry is **confirmed on the binary**, with three refinements that the implementer needs.

1. **Increment, cap, helper.** Every food-adding branch of SJOG `Get` calls kernel `0x3F14` with `(&food = DS 0x57A8, amount = 1, cap = 0x270F = 9999)`. The two SJOG call sites the ledger names (`push 0x57A8` at `0x1A44` and `0x1AB2`, calls at `0x1A50` and `0x1ABE`) cover **four tiles**: crop `0x2D`, and the three table-plate tiles `0x9A/0x9B/0x9C`. The ledger says "crops"; the cap applies to crops and plates alike. A third SJOG site `0x14EA` (`push 0x57A8` at `0x14DF`) covers food **objects** (NPC-slot item type 0x0F, and dungeon-chest food).
2. **What `counter_add` does at/over the cap** (kernel `0x3F14`): it computes `old + amount` as a 16-bit word, compares it **signed** (`jge`) with the cap, and if `>= cap` stores the cap. So `9999 + 1 -> 9999`, `9998 + 1 -> 9999`, and a value already above the cap (10000, 12345) is **clamped DOWN to 9999**. It is not a refusal: the routine has no failure path and returns nothing (`ret 6`, AX never read by any caller). The only edge where it is not a plain `min(cap, old+1)` is `old >= 0x7FFF` (the sum goes negative as int16, is `< 9999`, and the value just increments with 16-bit wrap). That edge is unreachable in play.
3. **At the cap nothing else changes.** The tile rewrite, the "needs redraw" flag, the success text, the karma decrement and the stats-dirty flag all execute **before or independently of** the `counter_add`, so a crop picked at food 9999 still consumes the crop (`0x2D -> 0x2C`), still prints `Crops picked!`, still costs karma 1 (if karma > 0) and still passes the turn. Only the food value differs (stays 9999 instead of becoming 10000).

**The "arena twin" is not a separate COMBAT.OVL routine in the binary.** The arena `G` key (COMBAT dispatch -> `0x096A` -> funnel `0x0544` code 0) calls thunk `0x7E06`, which is the same SJOG `Get` function (`SJOG 0x18CE`) the overworld uses. `ULTIMA.EXE 0x3282` calls the same thunk. The arena behaviour is the same instruction sequence running with `[0x5893] = 0xFF`, so tile access goes through the arena buffer. The "twin" is a port-side duplicate (TypeScript `resolveBoardGet`, native `combat.cpp` Get case). Both port duplicates already cap; both port **non-arena** paths do not. This matches the ledger's claim for the ports.

Confidence: high for every address and constant below. The only things not established from the binary are listed in section 8.

### 2.1 Kernel `counter_add` (ULTIMA.EXE `0x3F14`, Pascal calling convention, `ret 6`)

```
3f14: 55            push bp
3f15: 8b ec         mov bp, sp
3f17: 8b 5e 08      mov bx, [bp+8]      ; arg1 = pointer to word counter   (first pushed)
3f1a: 8b 07         mov ax, [bx]        ; old
3f1c: 03 46 06      add ax, [bp+6]      ; + arg2 = amount (16-bit add, wraps)
3f1f: 3b 46 04      cmp ax, [bp+4]      ; vs arg3 = cap
3f22: 7d 08         jge 0x3f2c          ; SIGNED compare
3f24: 8b 46 06      mov ax, [bp+6]
3f27: 01 07         add [bx], ax        ; below cap: *p += amount
3f29: eb 06         jmp 0x3f31
3f2c: 8b 46 04      mov ax, [bp+4]
3f2f: 89 07         mov [bx], ax        ; at/above cap: *p = cap
3f31: 5d            pop bp
3f32: c2 06 00      ret 6
```

Semantics: `s = int16(old + amount); if (s >= int16(cap)) *p = cap; else *p = old + amount (mod 65536)`.

* Already at cap: `old = 9999`, `s = 10000 >= 9999` -> `*p = 9999`. Unchanged. No error, no text.
* Above cap: `old = 10000 .. 32766` -> `*p = 9999` (clamp down). Exact boundary: `old = 32766` -> sum 32767 >= 9999 -> 9999; `old = 32767` -> sum wraps to `0x8000` (negative as int16) -> not `>=` -> `*p = 0x8000`.
* `old = 0x8000 .. 0xFFFF` (negative as int16): sum is negative or `0`, below cap, so `*p += amount` with wrap (`0xFFFF + 1 -> 0`).
* The sibling `0x3F54` (`counter_sub`, unsigned-style: `if [bx] > amt` ... else `0`) and `0x3EF0` (byte add, unsigned `jae`) are different routines; the food add never uses them.

### 2.2 The Get routine (SJOG.OVL file offset `0x18CE`, base `0xBF80`, so CS:IP `0xD84E`)

Entry thunk: `ULTIMA.EXE 0x7E06` = `9a ec 02 2e 07 | 0e | 00 | ea 4e d8 00 00`, overlay id `0x0E` (SJOG), target `0xD84E` = SJOG `0x18CE` + `0xBF80`.

Prologue and dispatch (every line read from `dis16.py SJOG.OVL 18ce`):

```

18dd  cmp byte [0x5893], 0x29 ; jae 0x18ea
18e4  call 0x179e ; jmp 0x1b2e                          ; loc 0x21..0x28 = dungeon room Get (chest loot), see 2.6
18ea  call 0x766c        (kernel 0x35EC dir prompt)  ; or ax,ax ; jne 0x18f4 ; jmp 0x1b2e   (cancelled = no action)
18f4  [bp-0xa] = [0x5876] (dx word) ; [bp-0xe] = [0x5878] (dy word)
1900  [bp-8]  = dx + byte [0x5896]   (target X)       ; [bp-0xc] = dy + byte [0x5897] (target Y)
191a  push 0x8de6 ; call 0x58d0                        ; prints DS 0x8DE6 = "\n"
1921  object-slot scan (see 2.6)                       ; slot hit -> call 0x1458 and exit
```

### 2.3 The four food branches (exact instruction sequences)

**Direction semantics** (kernel `0x35EC`, section 2.5): `dx = [0x5876]`, `dy = [0x5878]`. Key 1 -> `dec [0x5876]` (west), 2 -> `inc [0x5876]` (east), 3 -> `dec [0x5878]` (north), 4 -> `inc [0x5878]` (south). Cancel (ESC `0x1B` or space `0x20`) returns 0.

**Tile 0x2D (crop), site 1, `jmp 0x1a2a` at `0x19e2`:**

```
1a2a  push [bp-8] ; push [bp-0xc] ; call 0x8482 ; mov bx,ax
1a35  mov byte [bx], 0x2c                 ; crop tile -> 0x2C (unconditional, before the add)
1a38  or  byte [0x24e6], 2                ; turn/redraw mark
1a3d  mov ax, 0x8df4 ; push ax ; call 0x58d0   ; text "Crops picked!\n"
1a44  mov ax,0x57a8 ; push ax             ; &food
1a48  mov ax,1      ; push ax             ; amount 1
1a4c  mov ax,0x270f ; push ax             ; cap 9999
1a50  call 0x7f94                         ; kernel 0x3F14 counter_add (result unused)
1a53  mov byte [0xa9fa], 1                ; stats panel dirty (see 2.7)
1a58  cmp byte [0x5888], 0 ; jne 0x1a62 ; jmp 0x1b2e   ; karma == 0 -> exit
1a62  dec byte [0x5888]                   ; karma -= 1 when non-zero
1a66  jmp 0x1b2e
```

**Tile 0x9A, `jmp 0x1a6a`:**

```
1a6a  cmp word [bp-0xe], 1 ; jne 0x1a88        ; needs dy == +1 (target is SOUTH of the party)
1a70  push [bp-8] ; push [bp-0xc] ; call 0x8482 ; mov bx,ax
1a7b  mov byte [bx], 0x95                      ; plate tile -> 0x95
1a7e  or byte [0x24e6], 2
1a83  mov ax, 0x8e04 ; jmp 0x1a40              ; text "Mmmmm...!\n" then falls into 0x1a41 print and the 0x1a44 add above
1a88  mov ax, 0x8e10 ; jmp 0x1a8b              ; dy != +1: "Can't reach plate!\n", ret (no tile change, no food, no karma, no turn mark)
```

**Tile 0x9B, `jmp 0x1a92`:**

```
1a92  cmp word [bp-0xe], -1 ; jne 0x1ac4       ; needs dy == -1 (target is NORTH)
1a98  call tile ptr ; mov byte [bx], 0x95      ; 1aa3
1aa6  or byte [0x24e6], 2
1aab  mov ax, 0x8e24 ; push ax ; call 0x58d0   ; "Mmmmm...!\n"
1ab2  mov ax,0x57a8 ; push ax ; mov ax,1 ; push ax ; mov ax,0x270f ; push ax
1abe  call 0x7f94                              ; counter_add(food,1,9999)
1ac1  jmp 0x1a58                               ; karma step; NOTE skips 0x1a53 (no [0xa9fa]=1 on this branch)
1ac4  mov ax, 0x8e30 ; jmp 0x1a8b              ; "Can't reach plate!\n"
```

**Tile 0x9C, `je 0x1aca`:**

```
1aca  cmp word [bp-0xa],1 ; je 0x1ad6 ; cmp word [bp-0xa],-1 ; jne 0x1adc   ; dx == +-1: refuse
1ad6  mov ax,0x8e44 ; jmp 0x1a8b               ; "Can't reach plate!\n"
1adc  cmp word [bp-0xe],1 ; jne 0x1af0         ; dy == +1: tile <- 0x9B   (0x1ae8 call, 0x1aed mov byte [bx],0x9b)
1af0  cmp word [bp-0xe],-1 ; jne 0x1b04        ; dy == -1: tile <- 0x9A   (0x1afc call, 0x1b01 mov byte [bx],0x9a)
1b04  or byte [0x24e6], 2
1b09  mov ax, 0x8e58 ; jmp 0x1aae              ; shares the 0x1aae..0x1ac1 tail: "Mmmmm...!\n", counter_add at 0x1abe, then 0x1a58 karma
```

Summary table:

| target tile | accept test | tile written | text (DS, DATA.OVL file off) | add call | `[0xa9fa]=1` | karma |
|---|---|---|---|---|---|---|
| `0x2D` | always | `0x2C` | `Crops picked!\n` DS `0x8DF4` (`0x8E04`) | `0x1A50` | yes (`0x1A53`) | -1 if >0 |
| `0x9A` | `dy == +1` | `0x95` | `Mmmmm...!\n` DS `0x8E04` | `0x1A50` | yes | -1 if >0 |
| `0x9B` | `dy == -1` | `0x95` | `Mmmmm...!\n` DS `0x8E24` | `0x1ABE` | **no** | -1 if >0 |
| `0x9C` | `dx == 0` (any dy) | `dy==+1 -> 0x9B`, `dy==-1 -> 0x9A` | `Mmmmm...!\n` DS `0x8E58` | `0x1ABE` | **no** | -1 if >0 |

Refusal text, all identical bytes: `Can't reach plate!\n` at DS `0x8E10` (0x9A), `0x8E30` (0x9B), `0x8E44` (0x9C). A refusal writes nothing and does not set `[0x24E6]`. DS strings read from DATA.OVL: `0x8DE6="\n"`, `0x8DE8="Borrowed!\n"`, `0x8DF4="Crops picked!\n"`, `0x8E04/0x8E24/0x8E58="Mmmmm...!\n"`, `0x8E64="Nothing to get!\n"`.

Facts that matter for D-87:

* **No cap-specific text, no refusal, no second branch.** After `call 0x7f94` the next instruction (`0x1A53` or `0x1A58`) never tests AX.
* **Order**: tile write -> `[0x24E6] |= 2` -> text -> add -> flags -> karma. The tile and text are not conditional on the food value.
* **RNG**: none. The tile pointer (`0x4402`), the print (`0x1850`), the direction prompt (`0x35EC`) and `counter_add` do not call the RNG. Zero draws on all four success paths and all refusals.
* **Karma** is `[0x5888]` (byte), `cmp byte [0x5888],0 / jne / dec`: decrement only when non-zero.

### 2.5 Direction prompt (ULTIMA.EXE `0x35EC`)

`[0x5876] = [0x5878] = 0`, then loops on `0x266C` (key read) until the key is 1, 2, 3, 4, `0x1B` or `0x20`. Cancel prints DS `0xA2A0 = "Pass\n"` and returns 0 (so Get returns at `0x18F1 jmp 0x1b2e`). Directions print `North\n`/`South\n`/`West\n`/`East\n` (`0xA2A6/0xA2AE/0xA2B6/0xA2BC`) and return 1.

### 2.6 Other food-adding contexts (the same helper, same cap)

* **Object slots (SJOG `0x1458`, "pickup_object(type, qty, slot)")**, reached from Get's slot scan at `0x199F` and from the dungeon room routine at `0x18AB`. The scan (`0x1926..0x19BD`) walks the NPC/object table at DS `0x5C62` stride 8 (tile byte at +0, X at +2, Y at +3, Z at +4, quantity at +5, `0x5C5F + 8*slot` addresses the quantity), matches X, Y and (when `[0x5893] <= 0x7F`) Z, and accepts a slot whose tile byte is `< 0x10`, or `0x19`, or `0x1B`, or `(b & 0xFC) == 0xB4`. Type `0x0F` dispatches (`0x1740: cmp ax,0xf -> 0x14ca`):
  ```
  14ca  push [bp+6] ; push 1 ; push 0x20 ; call 0x5abe          ; number printer (kernel 0x3A3E), the quantity
  14d8  mov ax,0x8c6e ; push ax ; call 0x58d0                    ; " food!\n"
  14df  mov ax,0x57a8 ; push ax ; push [bp+6] ; mov ax,0x270f ; push ax
  14ea  call 0x7f94                                              ; counter_add(food, qty, 9999)
  14ed  jmp 0x177a                                               ; tail: clear slot (0x178B), [0x24e6]|=2, [0xa9fa]=1
  ```
  The same tail `0x14E2` is shared with gold (type 2, `mov ax,0x57aa; jmp 0x14e2`).
* **Dungeon chest room Get (SJOG `0x179E`, loc `0x21..0x28`)**: loops `si = 0..6` over the DS tables `0x41BC = [2,4,5,10,20,25,25]` (guard threshold), `0x41C4 = [31,0,3,3,3,7,7]` (max amount), `0x41CC = [15,2,7,8,13,255,255]` (item type); row 0 is food: quantity `rand(1,31)` and type `15`, passed to `0x1458` -> the `0x14EA` add. No crop tile logic there.
* **Other writers of food through the same `0x3F14`** (not pickups, listed for completeness; all use cap `0x270F`): CAST `0x05CF` (Create Food, `rand(1,3)`), TALK `0x06C4` (+1), SHOPPES2 `0x015D` (+1 per living member) and `0x045F` (+25 per unit; the loop then tests `cmp word [0x57a8],0x270f` at `0x0462`). Subtractors on food: ULTIMA.EXE `0x2B96` (hunger, `0x3F54`) and COMBAT `0x03A3` (` stole some food!`, `0x3F54`, amount 5).
* **The other two `0x3F14` callers in the executable** (`ULTIMA.EXE 0x2E39`, `0x4057`) and COMBAT `0x193E` / `0x1A51` add to HP / experience words (`0x55BC + (char << 5)`), not food. Verified by their pushed pointers.

### 2.7 Flags used by the branches

* `[0x24E6] |= 2` (`0x1A38`, `0x1A7E`, `0x1AA6`, `0x1B04`): set only on success, never on a refusal, never by the `Nothing to get!` fall-through. Both ports treat it as the turn mark (a success passes a turn). I did not disassemble its consumer.
* `[0xA9FA] = 1`: consumers in COMBAT (`0x06E2: cmp [0xa9fa],0 / je / call 0x8670 / mov [0xa9fa],0`) and MAINOUT (`0x05A3`) call the stats-panel redraw (kernel `0x2900`, derived by `0x8670 + 0xA290`, same address the executable calls at `0x2BC7`). The crop branch and the 0x9A branch set it; **0x9B and 0x9C do not** (they jump to `0x1A58`, below `0x1A53`). Presentation-only; I did not disassemble `0x2900` itself.

### 2.8 The arena path (COMBAT.OVL, base `0xA290`)

* COMBAT dispatch: key `0x47` ('G'): `jmp word cs:[bx-0x52a2]` table at file `0x0ACE` entry index 5 = `0xABFA` -> file `0x096A`: `mov ax,0x6e14 ; push ; sub ax,ax ; push ; call 0x544` (DS `0x6E14 = "Get-"`, code 0).
* Funnel `COMBAT 0x0544`: prints the prompt (`0x75C0 -> 0x1850`), tests the active-player flag (`test byte [bx-0x45ea],0x80`; if clear prints DS `0x6D98 = "Can't!\n"` and returns 1), then `cmp ax,0 / je 0x580`; code 0 -> `0x0580: call 0xffffdb76` = thunk `0x7E06`.
* So the arena runs SJOG `0x18CE` itself. With `[0x5893] = 0xFF` (set by the combat entry routine at `ULTIMA.EXE 0x5FB4: mov byte [0x5893],0xff`, after saving the old location to `[0x5894]` at `0x5FAB`):
  * `0x18D6`/`0x18DD` do not divert to the dungeon routine (0xFF is not in 0x21..0x28);
  * the slot scan skips the Z test (`0x1950: cmp dl,0x7f / ja 0x1964`);
  * `tile_ptr` addresses the arena buffer (`0xAD14 + (y<<5) + x`), so the tile writes (`0x2C`, `0x95`, `0x9A/0x9B`) hit the live arena map;
  * the torch branch skips the repaint call (`0x19FB: cmp [0x5893],0x80 / jae 0x1a05`), which is the only location-sensitive difference and is not a crop concern.
* COMBAT.OVL has **no** crop/plate code and none of the strings `Crops picked`, `Mmmmm`, `Can't reach plate` (searched every `.OVL` and the EXE: they exist only in DATA.OVL, and only SJOG pushes their DS offsets: `0x191A, 0x1A0A, 0x1A3D, 0x1A83, 0x1A88, 0x1AAB, 0x1AC4, 0x1AD6, 0x1B09, 0x1B28, 0x1750, 0x14D8`).
* COMBAT's own `0x57A8` reference (`0x039B`) is the food **theft** (`counter_sub`, amount 5), not a pickup.
* Therefore in the original the arena behaviour at the cap is identical to the overworld: food stays 9999 (clamps down from above), tile consumed, text printed, karma decremented, turn consumed.

## 7 Proposed fix and boundary test cases

**TypeScript (`game/src/core/game.ts`)**: add `import { addWordCapped } from "./counters.js";`, then line 6079 `this.state.food = addWordCapped(this.state.food, 1);` and line 6145 likewise. The arena (`combat.ts:4025`) and the object paths already match.

**Native (`native/core/src/quest_search.cpp` line 56)**: replace `++c.game.food` with `c.game.food = uint16_t(std::min<int32_t>(9999, int32_t(c.game.food) + 1))` (or a shared helper with the same body; `kFoodCap` exists in `enhanced.h`). Optionally align `loot.cpp:140` (and `:130` for gold) by dropping the `if(g.food<9999)` guard so a value above the cap clamps to 9999 like `counter_add`. Decision for the implementer: use the plain `min` (matches both ports' arena today and every reachable value) or the exact signed helper `s = int16_t(old + amount); old = (s >= 9999) ? 9999 : uint16_t(old + amount)`.
