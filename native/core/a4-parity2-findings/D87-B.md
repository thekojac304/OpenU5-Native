# D-87 (crop food cap) -- investigator B (ports-first lens)

Scope: read-only. Nothing in the repository was edited or built. Scratch scripts:
`findings/basescan.py`, `findings/census.py`, `findings/census_food.py` (all under the findings folder).
Every address below was disassembled in this session with `re/tools/dis16.py` (SJOG.OVL / COMBAT.OVL by file
offset, ULTIMA.EXE with `--exe`). DS strings are DATA.OVL file offset = DS + 0x10.

## 1 Verdict

D-87 is CONFIRMED and the original's behaviour is fully established statically:

* Every crop/plate pickup ends in the kernel routine `counter_add(&food, 1, 9999)` (ULTIMA.EXE 0x3f14). It is
  a SIGNED 16-bit saturating add: when `food + 1 >= 9999` it STORES 9999 (so it clamps DOWN from 10000+,
  it does not leave the value alone and it never refuses).
* The pickup is NEVER refused or altered by the cap: the tile change, the text, the repaint flag and the
  karma decrement all happen before/after `counter_add` on a path that does not read its result. At food =
  9999 the crop is still consumed ("Crops picked!", tile 0x2d -> 0x2c, karma -1 if nonzero), food stays
  9999. At food = 10000+ the first pickup lowers food to 9999.
* The increment is exactly 1, cap exactly 0x270f = 9999, no RNG, no sound, no clock advance inside the branch.
* There is NO separate arena/COMBAT.OVL crop routine. The "arena twin" is the SAME SJOG routine (cmd_get
  SJOG.OVL:0x18ce) reached from the combat command funnel (COMBAT.OVL 0x0544, code 0, call at 0x0580 ->
  kernel thunk 0x7e06). COMBAT.OVL has no crop/plate code and no food counter_add. Both ports' arena code
  (`combat.ts` 4021-4029, `combat.cpp` 1516) already caps, and it matches the binary for every food value a
  16-bit unsigned field can hold below 32767.
* Divergence: the OVERWORLD/TOWN paths of BOTH ports use a bare increment (TS `state.food++` x2 in
  `game.ts`, native `++c.game.food` in `quest_search.cpp`). It also applies to the three PLATE tiles
  (0x9a/0x9b/0x9c), which share the same two `counter_add` call sites. The fix must cover plates too.
* Crops exist only on small maps (towns/huts), not on the overworld/underworld (census in section 3.4).
  The word "outdoor" in D-87 means "outside combat".

Confidence: high for the logic; the only unproven items are runtime (no DOSBox witness) and two out-of-scope
questions (section 8).

### 2.2 counter_add, ULTIMA.EXE 0x3f14 (kernel "add_word_capped")

```
3f14: push bp
3f15: mov bp, sp
3f17: mov bx, word ptr [bp + 8]     ; arg1 = pointer (pushed first)
3f1a: mov ax, word ptr [bx]         ; 16-bit current value
3f1c: add ax, word ptr [bp + 6]     ; + arg2 = amount (16-bit, wraps)
3f1f: cmp ax, word ptr [bp + 4]     ; vs arg3 = cap (pushed last)
3f22: jge 0x3f2c                    ; SIGNED: sum >= cap
3f24: mov ax, word ptr [bp + 6]
3f27: add word ptr [bx], ax         ; sum < cap: *ptr += amount
3f29: jmp 0x3f31
3f2c: mov ax, word ptr [bp + 4]
3f2f: mov word ptr [bx], ax         ; sum >= cap: *ptr = cap   (CLAMP, up or DOWN)
3f31: pop bp
3f32: ret 6
```

Exact semantics (food is a word at DS:0x57a8, args pushed ptr, amount, cap):

* `sum = int16(food + 1)`. If `sum >= 9999` (signed) then `food = 9999`, else `food = (food + 1) & 0xFFFF`.
* food 9997 -> 9998; 9998 -> 9999; 9999 -> 9999 (stored again); 10000 -> 9999; 12345 -> 9999;
  32766 -> 9999.
* Signed quirk, unreachable in normal play: food 32767 -> sum 0x8000 = -32768 < 9999 -> food = 0x8000 (32768);
  food in 32768..65534 (negative as int16) -> food+1; 65535 -> 0 (wraps). Only a hand-edited save can get
  there. See section 8 for the decision this leaves to the implementer.
* AX on return is the amount (1) on the add path and the cap (9999) on the clamp path; the caller ignores it.
* The sibling kernel counters are different routines: 0x3ef0 add_byte_capped (cap 99), 0x3f36 (byte,
  floor 0 subtract), 0x3f54 (word, floor 0 subtract; used by COMBAT 0x03a3 for the 5-food theft).

### 2.4 Arena ("combat twin")

Not a separate routine. Facts:
* COMBAT.OVL 0x096a (key 'G'): `push 0x6e14 ("Get-")`, `sub ax,ax; push ax` (code 0), `call 0x544`.
* COMBAT.OVL 0x0544 funnel: `push [bp+6]; call 0x75c0` (print the echo via kernel 0x1850), index the actor
  record `[bx-0x45ea]` (bx = [0x589e]<<3) and `test ...,0x80`; if clear it prints `0x6d98 "Can't!\n"` and
  returns 1; otherwise `cmp ax,0 / je 0x580`: `0x0580: call 0xffffdb76` (-> kernel thunk 0x7e06 = SJOG
  cmd_get) `jmp 0x5b0` -> `sub ax,ax; ret 4`. So the arena runs the whole 2.3 routine with g_location =
  0xff: the object sweep compares floor only for location < 0x80 (0x1950-0x1962), the tile comes from the
  live buffer (kernel 0x4402, > 0x7f -> 0xad14 + (y<<5) + x), the only location test in the tail is the
  torch branch's repaint skip (0x19fb `cmp [0x5893],0x80 / jae`).
* In the arena loop, `[0xa9fa]` (set by the crop and 0x9a tail at 0x1a53) is consumed at COMBAT 0x06e2:
  `cmp byte [0xa9fa],0 / je 0x6f1 / call 0x8670 (-> kernel 0x2900, a loop of six calls to 0x2726 = status panel
  refresh) / mov byte [0xa9fa],0`. So crops/0x9a repaint the stats panel after the command; 0x9b/0x9c skip
  `0x1a53` and do not set it. (Port-visible only as a HUD refresh.)
* COMBAT.OVL has no crop, plate or food-increment code. Its only food references are 0x0380 `cmp [0x57a8],0`
  and 0x039b..0x03a3 (the 5-food theft via the floor-0 word subtract 0x3f54). Its `0x270f` immediates at
  0x193b and 0x1a4e push `0x55bc + member*32` (experience), not food. Census over all binaries of
  `mov ax,0x57a8; push ax; ...; mov ax,0x270f; push ax; call 0x3f14` (food counter_add): SJOG 0x14ea,
  0x1a50, 0x1abe; SHOPPES2 0x15d, 0x45f, 0x49c; TALK 0x6c4; (CAST 0x5bc area is Create-Food, separate).
  Only SJOG 0x1a50 and 0x1abe are crop/plate.
* Whether the crop is consumed in the arena: yes, identical to overworld: tile 0x2d -> 0x2c in the live
  buffer, at any food value. The arena always burns the command's turn (funnel returns `sub ax,ax`; the
  command loop sets `[bp-4]=1` at 0x083e), including rejects.

## 8 Unresolved

1. Runtime confirmation: all of the above is static disassembly; no DOSBox trace of a crop at 9999/10000 was
   made. What would settle it: a DOSBox run with a save whose food word (DS:0x57a8) is 0x270F / 0x2710, Get
   on a crop, read the word after. The static proof is complete enough that I rate this low risk.
2. Values >= 32767 (signed quirk, 2.2): the original keeps food+1 (wrapping at 65535 -> 0). The ports would
   clamp them to 9999 if `min` is used. Reachable only by a hand-edited save or a debug path; no Developer
   row exceeds 9999 (`debug_developer.cpp` range 0..9999). Decide whether to emulate the quirk or document it
   as deliberate.
3. The EXE dispatcher (0x3178) returns `[bp-2]` = 1 unless a case stores; the Get case does not (0x3282).
   That means the dispatcher always reports "turn consumed" for Get, which sits oddly with the port's "no
   turn for Nothing to get!/Can't reach plate!" rule that the notes derive from the `[0x24e6]` marker (I read
   0x24e6 at EXE 0x595e..0x598a as a viewport-redraw flag, not a turn flag). This is outside D-87 and I did not
   trace TOWN 0x158f / MAINOUT 0x0c00 further; it does not affect the cap fix because crop turn handling is
   identical at and below the cap.
4. Native HUD refresh: the original sets the status-panel dirty flag `[0xa9fa]` on the crop and 0x9a path
   only. `quest_search.cpp` emits only a Message for crops/plates (no PartyChanged). I did not check whether

5. `re/tools/callers_banda.py` BASES is wrong for COMBAT.OVL (and likely others, section 2.1). Any prior
