# D-82-A: the missing INIT.OOL underworld objects (binary-first derivation)

Investigator lens: binary first. Every claim in section 2 comes from instructions I disassembled in this session with
`re/tools/dis16.py` and my own wrapper `scratchpad/dz.py` (same capstone engine, adds kernel-call resolution and DS-string
annotation). Notes, the TypeScript reference and the C++ port were read only after the derivation was written down
(sections 4 and 5 compare against them). Nothing inside the repository was edited, built or run (no cmake, ninja, ctest, idf).
Scratch scripts: `scratchpad/dz.py`, `census.py`, `tbl_refs.py`, `zwrites.py`, `dsrefs.py`.

Conventions. Overlay addresses are FILE offsets. Kernel addresses (`K:xxxx`) are `ULTIMA.EXE` image offsets with the 0x800 MZ
header skipped (`dis16.py --exe`). `DS:xxxx` strings live in `DATA.OVL` at file offset `DS + 0x10`. Calls are quoted as the
disassembler prints them (`call 0xffffa3ae`) followed by the resolved kernel target.

---------------------------------------------------------------------------------------------------------------------------

## 1 Verdict

The original `.OOL` cycle is derived end to end. Summary of what the binary establishes:

1. There is ONE live object/actor table: `DS:0x5C5A`, 32 records x 8 bytes = 0x100 bytes, which is `SAVED.GAM + 0x6B4`
   (0x5C5A - 0x55A6). It always describes the map the party is currently on. The two outdoor worlds each have a PARKED copy
   of the same 0x100 bytes in a file: `BRIT.OOL` (g_floor == 0) and `UNDER.OOL` (g_floor != 0).
2. `SAVED.OOL` is 512 bytes = BRIT block (0x000-0x0FF) ++ UNDER block (0x100-0x1FF). `INIT.OOL` is 256 bytes and has the
   UNDER-block format; the new game writes `SAVED.OOL = 256 zero bytes ++ INIT.OOL` (FONT.OVL 0x0de7-0x0e2b, and the Ultima IV
   transfer path INTRO.OVL 0x1ddc-0x1df6 does the same). `Journey Onward` (INTRO.OVL 0x0e7c-0x0f99) splits `SAVED.OOL` into the
   working files `BRIT.OOL` and `UNDER.OOL`. `BRIT.OOL`/`UNDER.OOL` on disk are therefore runtime scratch files, not data.
3. The five objects are five 8-byte records inside the UNDER block: slot 23 `29 29 0e f2 ff 00 00 00` (tile 0x29 SkiffRight at
   (14,242), floor byte 0xFF) and slots 24-27 `1e 1e 67 e2 ff ..`, `1e 1e 69 e3 ff ..`, `1e 1e 6b e3 ff ..`,
   `1e 1e 6c e1 ff ..` (tile 0x1e DeadBody at (103,226), (105,227), (107,227), (108,225)). They are verbatim records of the
   live table, NOT terrain cells and NOT a separate representation. No transformation happens between file and table
   (K:7234 is a raw `int 21h/3Fh` of 0x100 bytes into `DS:0x5C5A`).
4. They become live only when the UNDER file is read into `DS:0x5C5A`. The read sites are exactly: kernel main loop after any
   town/dungeon session ends (K:0x012d-0x013c, selecting the file by `g_floor`), the moongate teleport when both ends are
   outdoors (K:0x4889-0x4898), and the waterfall at (54,138) (OUTSUBS 0x0538). The WHIRLPOOL teleport (MAINOUT 0x12b2) sets
   `g_floor = 0xFF` WITHOUT touching any `.OOL` (the table stays Britannia's).
5. A save never parks the live table. `CAST2.OVL` 0x113e-0x11a3 writes `SAVED.GAM` (live window, includes the live table) and
   `SAVED.OOL` = current on-disk `BRIT.OOL` ++ `UNDER.OOL`. Load reads both back verbatim. So the objects survive save/load in
   whichever of the two places currently owns them (live table if the party is outdoors in that world, otherwise the parked
   block).
6. Neither port places them (confirmed, section 4/5): both only use `init.ool` as the template for WRITING `SAVED.OOL`.

Answer to "how does the faithful representation relate to A4-SAVE3's terrain cell": the binary has no terrain-cell concept for
a parked skiff. It is a table record (slot identity matters because the recycler and `find_free_actor_slot` scan by slot), the
skiff keeps the terrain underneath it for walkability (here terrain 3 WaterCoast, which a foot party cannot enter, see 2.12),
and boarding it consumes the record (CMDS 0x0826 finds it with K:368e, CMDS 0x0949 clears it with K:3a74). Native's override cell (tile 0x129 in
`mapOverrides`, key `0:255:14:242`) differs in three observable ways: no slot, the cell becomes walkable on foot because
tile 0x129 is walkable, and it needs the `Board` path to read the tile instead of an object. See section 7 for the options.

Confidence: high for sections 2 and 3 (positive controls and an independent prior note agree, details in 2.0). Medium for the fix
design in section 7 (representation choices need a lead decision).

IMPORTANT INSTRUMENT WARNING for the whole A4-PARITY2 batch (found while validating): the overlay-base table in the task brief and
in `re/tools/callers_banda.py` BASES is wrong for about half of the overlays; any by-band census that uses it silently misses
callers. See 2.0.

### 2.1 The files (hex dumped in this session)

* `INIT.OOL`, `UNDER.OOL`, `BRIT.OOL`: 256 bytes each. `INIT.OOL` and `UNDER.OOL` are byte-identical (md5 11736cdb...);
  `BRIT.OOL` is 256 zero bytes (md5 348a9791...). `game/assets/init.ool` is 512 bytes = 256 zeros ++ `INIT.OOL`
  (verified byte for byte; sha256 d2ec1ae9f0472fcb...).
* `INIT.OOL` non-zero bytes, offsets 0xb8-0xdf (records 23-27, record i at 8*i):
  ```
  0x0b8 (slot 23): 29 29 0e f2 ff 00 00 00   tile 0x29, frame 0x29, x 14,  y 242, floor 0xff
  0x0c0 (slot 24): 1e 1e 67 e2 ff 00 00 00   tile 0x1e, frame 0x1e, x 103, y 226, floor 0xff
  0x0c8 (slot 25): 1e 1e 69 e3 ff 00 00 00   x 105, y 227
  0x0d0 (slot 26): 1e 1e 6b e3 ff 00 00 00   x 107, y 227
  0x0d8 (slot 27): 1e 1e 6c e1 ff 00 00 00   x 108, y 225
  ```
  Slots 0-22 and 28-31 are zero. Byte meanings are in 2.4.
* `INIT.GAM`: 4192 = 0x1060 bytes. `[0x2ED] = 0x0d` (g_location 13), `[0x2EE] = 0`, `[0x2EF] = 0` (g_floor), `[0x2F0..0x2F1] = 0x0f 0x0f`

### 2.2 Live-window addresses used below

`DS:0x55A6` is the base of the 0x1060-byte `.GAM` image (INTRO 0x0eb8-0x0ebf computes the length as `0x6606 - 0x55a6`).
`g_location = DS:0x5893` (+0x2ED), `g_floor = DS:0x5895` (+0x2EF), `g_x = 0x5896`, `g_y = 0x5897`, `g_transport_tile = 0x587c`.
Staging buffer for `.OOL` I/O: `DS:0xB21E` (BRIT half) and `DS:0xB31E` (UNDER half), 0x100 bytes each (0x200 contiguous).
DS strings (DATA.OVL file offset - 0x10): `SAVED.GAM` 0x31e6, 0x364b, 0x9698, 0xa0d6; `SAVED.OOL` 0x323f, 0x3641, 0x96a2, 0xa0cc;
`BRIT.OOL` 0x3249, 0x3989, 0x39de, 0x9684; `UNDER.OOL` 0x3252, 0x3266, 0x3992, 0x39e7, 0x39fb, 0x967a, 0x968e;
`INIT.GAM` 0x3345, 0xa060; `INIT.OOL` 0x334e, 0xa0c2; `BRIT.DAT` 0x3980/0x399f; `UNDER.DAT` 0x3976/0x39f1/0x325c.

### 2.3 File I/O primitives (kernel)

* `K:256e` `readfile(offset, len, buf, name)` (cdecl, `ret 8`): wrapper that selects the "disk" (`K:1eac`) and loops over
  `K:7234(offset, len, buf, name)` until it returns non-zero. `K:7234` (7234-7293): `int 21h ah=3Dh al=2` open, if offset != 0
  `ah=42h` lseek from start (`mov dx,[bp+4]; xor cx,cx`), `ah=3Fh` read `cx=[bp+6]` (0 means 0xFFFF) bytes to `[bp+8]`,
  close. No transformation, no zero fill.
* `K:25d8` `writefile(len, buf, name)` (`ret 6`): disk prompt loop then `K:7296` (7296-72ce): `ah=3Ch` create (truncate), `ah=40h`
  write `cx=[bp+4]` bytes from `[bp+6]` to handle from name `[bp+8]`, close.
* `K:251e(n)` selects the "disk" (n = 1, 2, 3, 4, 5, 0 appear). It is a floppy-era volume selector and is irrelevant on a hard
  disk; it explains the odd `K:1674` waits for `BRIT.DAT`/`UNDER.DAT` and the "re-write UNDER.OOL to disk 5" tails.
* `OUTSUBS:0x0368` (via thunk image 0x7a22, kernel callers use `call 0x7a22`): `world_filename()`:
  ```
  036e 803e955800     cmp byte ptr [0x5895], 0       ; g_floor
  0373 7507           jne 0x37c
  0375 c746fe8939     mov word ptr [bp-2], 0x3989    ; "BRIT.OOL"
  037c c746fe9239     mov word ptr [bp-2], 0x3992    ; "UNDER.OOL"
  ```
  The predicate is `g_floor == 0` (not `> 0x7f`).

### 2.4 The live table and its record layout

Location and size: `DS:0x5C5A .. 0x5D59` (32 x 8). Slot 0 is the party's own vehicle record (hull = `0x5C5F`, skiffs = `0x5C61`,
see CMDS 0x08f4/0x0936: `mov [0x5c5f], al`, `mov [0x5c61], al`; CAST2 0x1075 writes `0x1c` to `[0x5c5a]`/`[0x5c5b]`).

Writer `K:3a74` `write_slot(idx, +5, +4, +3, +2, +1, +0)` (`ret 0xe`): `si = idx << 3` then stores to `[si+0x5c5a]` (+0), `+0x5c5b` (+1),
`+0x5c5c` (+2), `+0x5c5d` (+3), `+0x5c5e` (+4), `+0x5c5f` (+5). It never writes +6/+7.

| byte | meaning (evidence) |
|---|---|
| +0 | tile byte in the HIGH sprite bank (sprite = +0x100): 0x1e DeadBody, 0x29 SkiffRight. Class selector for the recycler (2.6). Free slot iff +0 == 0 (`SJOG:0x0012 cmp byte [bx+0x5c5a],0`) |
| +1 | live animation frame, equal to +0 when placed (MAINOUT 0x117c-0x11d5 toggles 0x2c..0x2f; K:6856/K:6b4a copy +0 to +1) |
| +2, +3 | x, y |
| +4 | floor byte: 0 = Britannia, 0xFF = underworld (compared with g_floor in K:368e and MAINOUT 0x00b6) |
| +5 | ship hull (CMDS 0x08dc), chest contents/trap bit 0x80 (CAST 0x03de sweep), plot-item index (OUTSUBS 0x0566) |
| +6 | not referenced by any indexed access I could find; not derived |
| +7 | skiffs aboard a ship (CMDS 0x08fe -> 0x5c61), a counter for monsters (MAINOUT 0x1a39 `inc byte [si+0x5c61]`) |

There is NO flag byte separating "monsters" from "objects": the discrimination is by the +0 value and by slot position, see 2.6.

Position lookup `K:368e(floor=[bp+4], y=[bp+6], x=[bp+8])` (kernel 0x368e-0x36fe): scans slots 1..31 ascending (`si = 0x5c62`),
matches `slot.x == x && slot.y == y` and, when `g_location <= 0x7f`, `slot.z == floor` (`cmp cl,0x7f / ja` skips the floor test
for g_location > 0x7f, i.e. combat); returns the slot's +0 byte and sets `[0x5876]` to the slot index (32 when not found).
`K:3702` is the same scan from slot 31 downward. Callers of `K:368e`: 18 (listed in 3.4).

### 2.6 How the allocator treats slots (why slot positions matter)

* `K:3868(lo, hi, near)` (ret 6): scans slots 1..23 ONLY (`3870 mov cx,1` ... `38cf cmp cx,0x18 / 38d2 jl`), accepts `+0 in [lo,hi]`,
  never accepts 0xB5 (`388f cmp al,0xb5`), and with `near != 0` only slots outside the 11 x 11 party window. Ten kernel call sites
  (3.4). `K:38e4` is the cascade: free slot (0,0), then bands `0x01-0x0f`, `0x80-0xff`, `0x10-0x11`, `0x30-0x7f` off-screen then
  on-screen, finally any tile.
* `SJOG:0x0000` `find_free_actor_slot`: `mov dx,0x20 / dec dx / js end / cmp byte [bx+0x5c5a],0 / jne` scans 31 down to 0 and returns
  the first slot with +0 == 0 (a result of 0 is ambiguous with "none").
* Consequences for the five records: slot 23 is the LAST recycled slot, so the skiff permanently removes one monster slot while
  present; its +0 (0x29) lies in none of the earlier cascade bands, so only cascade call 10 (tile 0x00-0xff) could evict it.
  Slots 24-27 are in the object region (31 down), never touched by the 1..23 recycler. The Amulet/shard reseed occupies 28-31
  (2.10), so the five new records pack directly below it.

### 2.8 The kernel dispatch loop and every table swap

Kernel main loop (`ULTIMA.EXE` 0x00b8-0x017d):
```
00b8 [bp-2]=0
00bd cmp byte [0x5893],0 / jne 0xd1 ; 00c4 call 0x7a3a (MAINOUT outdoor loop thunk) ; [bp-2]=1
00d1 cmp byte [0x5893],0 / jne 0xdb ; 00d8 jmp 0x16e                      ; outdoors again: nothing to reload
00db cmp byte [0x5893],0x21 / jae 0x104                                      ; < 0x21 = small map
00f7 call 0x7a46 (town load, arg = [bp-2]||[bp-8]) ; 00fa call 0x7a52 (town loop)
0104 K:251e(2); 010e call 0x7a16 (dungeon)
0116 ... K:251e(1); wait BRIT.DAT (0x1393)
012d e8f278   call 0x7a22                     ; world_filename()   (OUTSUBS:0368)
0130 push ax ; 0131 b85a5c mov ax,0x5c5a ; 0135 b80001 ; 013b push 0
013c e82f24   call 0x256e                     ; READ  readfile(0, 0x100, 0x5c5a, world_filename())
013f cmp byte [0x5893],0 / jne 0x16e ; 0146 cmp byte [0x5895],0 / je 0x16e
015f call 0x7a22 ; ... 016b call 0x25d8       ; WRITE the same 0x100 bytes back to UNDER.OOL (floppy re-write)
```
All swap events (every site that touches `DS:0x5C5A` against a `.OOL`; "world(z)" = `BRIT.OOL` if z == 0 else `UNDER.OOL`):

| event | site | action |
|---|---|---|
| R1 leave a town/dungeon | K:0x012d-0x013c | `L := file world(g_floor)` (g_floor was set by the exit, 2.9) |
| W1 `Enter` command on a keep/town/castle/village tile | OUTSUBS 0x040c-0x0418 (fn 0x388, via thunk 0x7bba from MAINOUT 0x097e) | `file world(z) := L`, then g_location = idx+1, g_floor = 0, (15,30) |

### 2.12 Representation and behaviour of the five records

* Each is a normal 8-byte slot. The moment `UNDER.OOL` is read into `0x5C5A` they are slots 23-27 and everything in 2.4/2.6 applies.
* Movement (MAINOUT 0x01fe-0x02b6, the outdoor step): `obj = K:368e(floor, y+dy, x+dx)`; if an object is present the cell is
  BLOCKED unless the party's transport/object pair is in an allow list: for a foot party (g_transport_tile < 0x20) objects with
  +0 in 0x24..0x2b (ships/skiffs), 0x1b (carpet) and 0x10/0x11 (horses) are allowed; every other value, including 0x1e DeadBody,
  blocks. If allowed, the TERRAIN byte of that cell is then tested by `K:2c4c(terrain, transport)` (class from `DS:0x54f4 +
  (transport>>2)`; foot is class 0 -> `K:2bd4`: bit `0x80 >> (t&7)` of `DS:0x54d4 + (t>>3)` set = blocked).
  Terrain under the five records (my decode of UNDER.DAT, same as the port's map): skiff cell (14,242) = tile 3 WaterCoast
  (bitmap blocked), its neighbours (13,242) = 49 and (14,243) = 48 (passable), (14,241) = 2; bodies (103,226), (105,227), (107,227),
  (108,225) = tile 5 Grass (passable); the Amulet cell (105,225) = 48 (passable).
  Consequence: the four bodies block foot movement (as objects); a foot party cannot step onto the skiff cell (terrain), and
  `Board` (CMDS 0x07f6-0x0951) requires standing on that very cell (`K:368e(g_floor, g_y, g_x)` at 0x0826), foot only
  (`L:06ee`, tile 0x1c/0x1d), so the new-game skiff looks unobtainable by the paths I checked (carpet class could enter the cell
  but cannot board). I did not read every movement path (ships, spells, Klimb), so "unobtainable" is "not found", not proved.
* Boarding a skiff: CMDS 0x0898-0x08b5 (`and al,0xfc; cmp al,0x28`), prints "skiff", sets `[0x587c] := object byte`, falls to the
  common epilogue 0x093e `K:3a74(slot,0,0,0,0,0,0)` (clears the record) and does NOT read or write hull/skiffs (that copy,
  0x08dc-0x0936, is the frigate branch only).

### 2.13 Other facts relevant to the ports' modelling

* Entering a small map wipes the live table in the town loader: `TOWN.OVL 0x0fea-0x0ff4` (`mov cx,0x100; mov di,0x5c5a; rep stosb`
  with al = 0) and `TOWN 0x120a-0x1216` (zeroes +0 of slots 1..31 when the reload flag is set). The port comments that attribute
  this memset to `MAINOUT 0x0857` (`game.ts:6964`, `saveNative.ts:509`, `:954-955`) cite the wrong site: MAINOUT 0x0857 is the
  PARK WRITE (K:7a22 -> K:25d8), the wipe is in TOWN.
* `g_hull`/`g_skiffs` are slot 0's +5/+7 (`0x5C5F`, `0x5C61`), so every table swap replaces them with the parked block's slot 0
  (zeros in `INIT.OOL`'s UNDER block). The ports keep them as global state.
* `K:47f4` (moongate) parks and reloads only the 0x100-byte table, so wandering monsters are per-world in the binary (parked
  with the table). The ports keep one enemy list (adjacent divergence, section 8).

## 7 Proposed fix and boundary test cases

### 7.1 What the original does at new game (the target behaviour)

New journey: BRIT parked block = 256 zeros, UNDER parked block = `INIT.OOL`; live table = whatever the starting small map (Iolo's Hut,
location 13) builds; the UNDER block becomes the live table at the first world swap into the underworld (2.8). The five records
appear there verbatim.

### 7.2 Where to put it (reference first, then native, per the "fix the reference at the pinned layer" rule)

* Seed at the NEW-JOURNEY layer, not in the import layer. Reference: a pure function (say `seedNewGameWorldObjects(state, initOol)`)
  called from the new-game entry points (`Game` constructor new-game branch `game.ts:1025`, and the `main.ts:907` creation flow), NOT from
  `createBaseGame` (`state.ts:526`) because `saveNative.ts:1065` reuses it for imports and the parity runners reuse it. Native: in the
  `CreateInitialSave` branch right after `objects_.clear()` (`alpha_runtime.cpp:3236`) and in the host fixture twin
  (`host_tests/alpha_runtime_host_fixture.cpp:116-117,160`).
* Data source: parse the UNDER block (offset 0x100) of the pack's `init.ool` (reference: `game/assets/init.ool`; Native:
  `resources_.initial_ool`) so the five records are not re-typed. Rule: every record `1..31` with `+0 != 0`, tile = `+0 + 0x100`,
  x/y/floor from +2/+3/+4, slot = record index. Classify by +0: `(b & 0xfc) == 0x28` skiff, `(b & 0xf8) == 0x20` frigate,
  `(b & 0xfe) == 0x10` horse, otherwise inert prop (the DeadBody).
* Fix the template provenance in the extractor: build `init.ool` as `zeros(256) ++ INIT.OOL` (FONT.OVL 0x0e11-0x0e2b), keeping the
  current `BRIT.OOL ++ UNDER.OOL` only as a consistency check. Today the two coincide (sha256 d2ec1ae9...), but a user whose DOS tree
  has been played produces a different `init.ool`, and the earlier note (`moonstone-loc-y-pozo-doom.md` 2.5) even described a BRIT.OOL
  with slot 0 at (86,107): this tree's file has none.

### 7.3 Representation decision to be taken by the lead

Option A (object, faithful to the table): skiff as `ship` kind (tile 0x129) or a new `skiff` class, slot 23; bodies as `prop`, slots 24-27.
Requirements: (a) the skiff must not change `shipHull`/`shipSkiffs` on Board (reference: leave `hull`/`skiffs` undefined; Native:
`ship_at` must return false or not copy for skiff tiles); (b) the cell must keep the TERRAIN's walkability underneath: with the
current compositor (object tile replaces terrain) tile 0x129 is walkable and a foot party could step onto the water cell and board,
which the binary forbids (2.12). Either the compositor keeps terrain walkability for vehicle objects, or the skiff is accepted as a
declared divergence. (c) Export: the PC bridge already handles pool ships with skiff tiles (`pc_save.cpp:283-285`); import still converts
skiffs to terrain cells (`read_vehicles`), so a DOS import and a new journey would give two different representations of the same
record unless the bridge is updated too.
Option B (terrain cell, consistent with A4-SAVE3): seed `mapOverrides["0:255:14:242"] = 0x129` and the four bodies as `prop`.
Cheapest, round-trips with the bridge, but loses the slot, makes the water cell walkable (same walkability issue), and cannot express
slot-pool effects. Not faithful.
The binary-faithful floor for an object is: record in the table, terrain unchanged underneath.

### 7.4 Encoder issues the seed would expose (must be handled or declared)

1. `writeNativeWorldObjects` (`saveNative.ts:564`) and `object_table` (`persistence.cpp:142`) write all ship/horse objects of
   location 0 with the party's floor. Seeding the skiff at floor 255 would make a surface save emit it into the Britannia live table
   (`.gam`), where the DOS game would show it at (14,242) on the surface. Filter by `o.floor === state.position.floor` for the live table
   and route the other floor's objects to the parked block (this is what `pc_save.cpp:229-300` does for the PC export).
2. `prop` objects are not written to the `.gam` live table by either encoder (`saveNative.ts:570-572`, `persistence.cpp:144-145`); in the
   underworld the four bodies would be missing from `0x6B4` (they still exist in the sidecar and in the template UNDER block).
3. `buildNativeOol`/`build_ool` clear slots 1..23 of the current world's block (`saveNative.ts:606-650`, `persistence.cpp:119-123`), so a
   save in the underworld drops slot 23 (the skiff) from the exported UNDER block. The binary keeps the parked block verbatim. Preserve
   reserved slots (the TS function already has a `reservados` parameter, unused by `buildNativeOol`).

### 7.5 Boundary test cases (RED first; reference then native)

1. New journey state: `worldObjects` (reference) / pool (Native) contains exactly five entries with (slot, +0, x, y, floor) = (23, 0x29, 14, 242, 255),
   (24, 0x1e, 103, 226, 255), (25, 0x1e, 105, 227, 255), (26, 0x1e, 107, 227, 255), (27, 0x1e, 108, 225, 255); none with floor 0. Derive the
   expectation from the 40 bytes `INIT.OOL[0xb8..0xdf]`, not from literals.
2. Surface save of a new journey: `SAVED.OOL == init.ool` (already pinned by `frontend_test.cpp:166`); the `.gam` bytes `0x6B4+0xb8 .. +0xdf`
   are all zero (guards the floor leak 7.4.1).
3. Underworld save: `.gam` live table contains the five records verbatim (needs 7.4.2 for the bodies); exported UNDER block unchanged for slots
   23-27 (needs 7.4.3).
4. Collision with the reseed: in the underworld with Amulet and three shards not taken, the table has slots 23-27 from the seed and 28 (0xb7 at
   105,225) and 29-31 (0xb4) from `hydrateUnderworldPlot`; `find_free_actor_slot` (31 -> 1) returns 27 only after 28-31 are used and 22
   or lower after 23-27 are used; the recycler scan range 1..23 treats slot 23 as occupied.
5. Walk: a foot party at (13,242) cannot enter (14,242) (terrain WaterCoast), at (103,225) cannot enter (103,226) or the other three body
   cells (object block); the same party walks (105,225).
6. Board: standing on a skiff object (synthetic) leaves `shipHull`/`shipSkiffs` unchanged; the record is cleared (CMDS 0x0949).
7. DOS import round trip (`check-pc-save.ts` TS8, bridge P10/T5/T6): a DOS save with the new-game UNDER block still yields the skiff once on export.
8. Whirlpool path (decision needed): binary leaves the Britannia table live under `g_floor = 0xFF` and reseeds slots 28-31 into it (2.8); the
   five objects are NOT visible after a whirlpool descent until a table swap. State explicitly whether the port reproduces that.
9. Negative control for the extractor change: `init.ool` built from `INIT.OOL` equals the committed asset (sha256 d2ec1ae9f0472fcb...) and differs from a
   `BRIT.OOL ++ UNDER.OOL` taken after a played session.
