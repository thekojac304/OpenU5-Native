# D-82 (lens C: cross-check) - the INIT.OOL / UNDER.OOL underworld objects

Investigator: D82-C. READ-ONLY (nothing in the repository was edited, no build or ctest was run).
Scripts and logs are under `findings/d82c/` (list in Appendix A); every address below was disassembled in this
session with capstone over the shipped binaries in `original/u5/ultima5`, unless a line says SECONDARY.

Conventions: `FILE.OVL:0xNNNN` = FILE offset of the overlay (what `dis16.py` prints); `ULTIMA.EXE:0xNNNN` = image
offset with the MZ header (0x800 bytes) skipped, i.e. the notes' CS:IP; `DS 0xNNNN` = DATA.OVL string address
(file offset = DS + 0x10). "Window" = the kernel's live-state window `DS:[0x55A6, 0x6606)` = 0x1060 bytes =
`SAVED.GAM` verbatim. "Table" = the 32-record x 8-byte actor/object table at `DS:0x5C5A` (= window +0x6B4).

## 1. Verdict

The derivation is finished. The original never reads INIT.OOL, UNDER.OOL or BRIT.OOL at new-game startup, and it never
"loads" them into the table at game start. What it does, proven from two independent writers, one reader, one saver,
the file bytes and the terrain data:

1. A new game WRITES `SAVED.OOL` (0x200 B) = **0x100 zero bytes (BRIT block) ++ INIT.OOL (UNDER block)**, and a
   `SAVED.GAM` from INIT.GAM whose table (+0x6B4..+0x7B3) is all zero. Two independent entry points do it identically:
   Create Character (`FONT.OVL:0x0DE7-0x0E3D`) and Transfer-from-Ultima-IV (`INTRO.OVL:0x1363-0x1E08`).
2. Journey Onward (`INTRO.OVL:0x0F26-0x0F89`) splits SAVED.OOL back into `BRIT.OOL` (first 0x100) and `UNDER.OOL`
   (second 0x100); the live table comes from SAVED.GAM (window), not from the .OOL files.
3. The `.OOL` files are the parking lot of the world the party is NOT in. The table at DS:0x5C5A belongs to the
   world the party is currently outdoors in (or to the interior it is in; the one exception is right after a whirlpool, 2.8). It is dumped to a world file
   at 7 call sites (5 through `world_filename`, `OUTSUBS.OVL:0x0368`: `g_floor == 0` -> BRIT.OOL, else UNDER.OOL; 2 with hard-wired names in the waterfall) and re-read
   at 3 call sites (2 through `world_filename`, 1 hard-wired): 0x100 bytes, whole table, no transformation.
4. So the five INIT.OOL records become live, byte for byte, on the FIRST ARRIVAL in the underworld by any of: moongate
   (`ULTIMA.EXE:0x4889-0x4898`), waterfall (`OUTSUBS.OVL:0x0529-0x0538`), return from a town/dungeon whose exit leaves
   `g_floor = 0xFF` (`ULTIMA.EXE:0x012D-0x013C`, which also covers `dng_exit`). The ONE underworld arrival that swaps
   nothing is the whirlpool (`MAINOUT.OVL:0x12B2`): there the Britannian table stays live under `g_floor = 0xFF`.
5. Representation: five ordinary 8-byte table records (`tile, tile, x, y, floor=0xFF, +5, +6, +7`) in slots 23..27:
   slot 23 `29 29 0e f2 ff 00 00 00` (tile byte 0x29 = sprite 0x129 SkiffRight at (14,242)); slots 24-27
   `1e 1e 67 e2 ff ..`, `1e 1e 69 e3 ff ..`, `1e 1e 6b e3 ff ..`, `1e 1e 6c e1 ff ..` (tile byte 0x1E = sprite 0x11E
   DeadBody at (103,226), (105,227), (107,227), (108,225)). Slots 28-31 are the neighbouring status objects that
   `OUTSUBS.OVL:0x0566` re-writes on every underworld outdoor entry (Amulet at (105,225) in slot 28, shards in 29-31).
   Nothing in the binary distinguishes an "object" from a "monster" except the tile byte (see 2.9).
6. They survive save/load exactly as the table does: the active world's table rides in SAVED.GAM +0x6B4, the other
   world's table in SAVED.OOL (BRIT block at buffer 0xB21E, UNDER block at 0xB31E).

Both ports differ from the binary only by omission: neither places the five records at new game (4.1, 5.1); each uses
`init.ool` only as a template for WRITING SAVED.OOL. The A4-SAVE3 bridge already models the table split correctly
(its `table_for()` = live table for the party's world, parked block otherwise, which is exactly what the binary does)
and already imports the seed skiff as a terrain cell `0:255:14:242 -> 0x129`.

Confidence: HIGH for the file/loader chain and the record contents; MEDIUM-HIGH for the consumer behaviour (blocking,
boarding, drawing) because it is read from code, not witnessed in DOSBox; see Section 8 for exactly what is open
(chiefly: whether a DOS player can ever reach/board the skiff, the hull/skiffs reset a world swap implies, and
the ports' tile-replacement representation).

### 2.2 The two file primitives (every game-file read/write goes through them)

`ULTIMA.EXE:0x256E` read_file_block_with_disk_retry, `ret 8`, args pushed `(name, dest, len, offset)`:
loops `call 0x7234` until it returns non-zero (`25ac-25bd`). `0x7234`: `mov ah,3dh` open (mode 2, name `[bp+0xa]`), if
`[bp+4] != 0` `mov ah,42h` lseek from start with `cx = 0, dx = [bp+4]` (16-bit offset), `mov ah,3fh` read with
`cx = [bp+6]` (0 -> 0xFFFF) into `dx = [bp+8]`, close. On failure it calls the error vector and returns 0 (-> retry).

`ULTIMA.EXE:0x25D8` write_whole_file_with_disk_retry, `ret 6`, args `(name, src, len)`: `0x2631: call 0x7296`:
`mov ah,3ch` create (`cx = 0`), `mov ah,40h` write `cx = [bp+4], dx = [bp+6]`, close. A file is always re-created whole.

`0x251E` is a volume/group selector (`0x252D-0x253E`: arguments 2 and 5 are mapped to 1, the result is stored in `[0xA9BD]`); it
moves no file content, so the `push 1/3/5 ; call 0x251e` pairs around the .OOL calls are not part of the data flow. Closure test (`d82c` scan of `b4 40 cd 21`, `b4 3c cd 21`): the only
file-CREATING instruction in all binaries is `ULTIMA.EXE:0x72A1` (inside 0x7296); `0x25D8` has exactly 17 callers
(Section 3.2) and every one of them writes SAVED.GAM, SAVED.OOL, BRIT.OOL or UNDER.OOL. There is no other writer of these files.

### 2.8 Underworld arrivals: which swap and which do not

The 24 instructions that write `g_floor` (`d82c/s10_gfloor_writers.py`, same count as `gfloor-146-acta.md` section 3) set an outdoor underworld floor of
0xFF at exactly these places: TOWN exit when `g_location == 0x19` (`TOWN.OVL:0x07C5-0x07D3`, "Exit to Underworld!"), `dng_exit` when `g_floor != 0`
(`DUNGEON.OVL:0x1D25-0x1D2C`, stub `0x7C9E`, callers `CAST.OVL:0x0FF5`, `DNGLOOK.OVL:0x1089`), moongate (`ULTIMA.EXE:0x4856`, the value comes from `[bx+0x5848]`), waterfall
(`OUTSUBS.OVL:0x0515`), whirlpool (`MAINOUT.OVL:0x12B2`). The other 0xFF writers are not outdoor arrivals: `BLCKTHRN.OVL:0x068C, 0x08E7` (palace basement, small-map floor -1) and
`ULTIMA.EXE:0x608E` (combat return restores the saved pair). Each outdoor arrival except the whirlpool is followed by a table read of `world_filename(g_floor)`: the town and dungeon exits
return to the main loop, whose `0x012D-0x013C` read follows; the moongate and waterfall read in place.

The whirlpool (`MAINOUT.OVL:0x1248`, only caller `MAINOUT.OVL:0x1399`; `0x125A-0x125E` tile class `(+0 & 0xFC) == 0xEC`):

```
126e: ... clear the whirlpool record (+0,+1 := 0) ; "\nWHIRLPOOL!\n" (DS 0x6b04) ; spin animation (kernel 0x43ae) ; call 0x109e
12b2: c6069558ff  mov byte [0x5895],0xff        ; g_floor = 0xFF
12b7: [0x5896]=0x22 ; 12bc: [0x5897]=0x12       ; (34,18)
12c1: call 0 (MAINOUT:0x0000 re-init) ; jmp 0x1313
```

No table write or read. After a whirlpool the live table is still the BRITANNIAN table with its records' `+4 == 0` while
`g_floor == 0xFF`; `find_object_at_xy` and the compositor compare `+4` with `g_floor` (2.10), so those records are invisible, and
the next departure writes them into UNDER.OOL (`world_filename(0xFF)`), destroying the seeds. The INIT.OOL seeds therefore never appear
for a player whose first underworld arrival is the whirlpool, and are lost for good afterwards. (A binary quirk; see 7 and 8.)

Adjacent consequence of the same mechanism (derived statically, NOT witnessed): slot 0 of the table is the party's vehicle record
(`g_hull = slot0+5 = 0x5C5F`, `g_skiffs = slot0+7 = 0x5C61`; `ULTIMA.EXE:0x5394` rewrites slot 0 +0..+4 every frame, +5/+7 are not touched).
A swap replaces slot 0 with the parked world's slot 0, whose new-game value is all zero (INIT.OOL slot 0 = 0, BRIT block = 0).

### 2.9 Record layout and slot roles (the representation)

Record = 8 bytes at `0x5C5A + 8*slot`, written by kernel `0x3A74` `ret 0xE` (arguments are PUSHED in the order +0, +1, +2, +3, +4, +5, slot, so slot is `[bp+4]` and +0 is `[bp+0x10]`; `3a7f..3aa5`):

| byte | meaning (code that proves it) |
|---|---|
| +0 | tile class byte; sprite = +0 + 0x100. Free slot <=> +0 == 0 (`SJOG.OVL:0x0012 cmp byte [bx+0x5c5a],0`, `ULTIMA.EXE:0x37B6`, `0x3868`) |
| +1 | animation/frame byte; the compositor draws THIS byte (it pushes/stores the byte at +1: `0x5525-0x5534`, `0x55E6-0x55FE`); equal to +0 at placement |
| +2 / +3 | X / Y (`find_object_at_xy` compares `[bp+8]` with +2 and `[bp+6]` with +3, `0x36AD-0x36BB`) |
| +4 | floor/world: for `g_location <= 0x7F` `find_object_at_xy` also requires `+4 == [bp+4]` = the caller's floor (`0x36C0-0x36D2`), and the compositor requires `+4 == [0x5895]` (`0x549A-0x54A2`) |
| +5 | hull (ships), loot/contents elsewhere (seeds: 0) |
| +6 | mover state (seeds: 0) |
| +7 | skiffs aboard (ships); seeds: 0 |

Slot roles in the OUTDOOR table:

* slot 0 = the party's vehicle (composed each frame from `[0x587C], [0x5896], [0x5897], [0x5895]`, `ULTIMA.EXE:0x53A6-0x53BF`);
* slots 1..23 = the spawn/recycle pool: `0x3868(lo,hi,flag)` scans `cx = 1..0x17` ascending (`cmp cx,0x18 ; jl`), accepts `lo <= +0 <= hi`, never tile 0xB5 (`0x388F`), and with `flag != 0` only records outside the 11x11 window.
  `0x38E4` calls it ten times (`0x38EF, 0x3905, 0x391D, 0x3935, 0x394D, 0x3964, 0x397B, 0x3992, 0x39A9, 0x39BF`): `(0,0,0)` = a free slot; then the classes `(1..0xF)`, `(0x80..0xFF)`, `(0x10..0x11)`, `(0x30..0x7F)`,
  each first with `flag = 1` (off-screen) and then, after the four classes, again with `flag = 0` (`0x3959-0x39A9`); last resort `(0,0xFF,0)` (`0x39B5-0x39C2`, any tile but 0xB5). Callers of `0x38E4`: Section 3.
  Tile bytes 0x1E and 0x29 are in none of the eight class ranges; only the last-resort call can take slot 23 (the skiff), and only when slots 1..22 offered nothing; slots 24..31 are outside the 0x3868 scan altogether;
* slots 1..31 = swept by `find_object_at_xy` (`0x36A6`: `si = 0x5C62`, stop `0x5D5A`) and the purchase/loot allocator `SJOG.OVL:0x0000` (31 downwards, first `+0 == 0`, 0 = none; callers: `SJOG.OVL:0x0FCC`);
* slots 23..27 (INIT seeds) and 28..31 (status objects) are simply the high end of the same table.

Monster vs object (outdoors): there is no type field; `MAINOUT.OVL:0x105C` `is_mobile_actor_tile(+0)` decides:
`0x2C..0x2F -> 1` (pirate frigate), `< 0x80 -> 0`, `0xB4..0xB7 -> 0` (crown/sceptre/amulet items), `0xE8..0xEB -> 0`, everything else `>= 0x80 -> 1`.
`MAINOUT.OVL:0x1A60` (outdoor world turn, stub `0x7B72`) sweeps slots 31 -> 1 with it: only mobile classes move, and a second pass (`0x1AE0-0x1B32`)
zeroes mobile records more than 0x1F cells outside the chunk window (`0x1B1F`: six zeros then the slot pushed, `call 0x3A74`). Tile bytes 0x29 and 0x1E are `< 0x80`:
the seeds never move and are never despawned by the world turn. (`MAINOUT:0x1A60` callers: `MAINOUT.OVL:0x0448, 0x0468, 0x0471, 0x069D, 0x0D11`; classifier callers `0x1AC1, 0x1AF5`.)

### 2.10 The consumers of a seed record

* Drawing (`ULTIMA.EXE:0x5394`, 11x11 window, sweeping slots 31 -> 0 with `[bp-0xa] = 0x1f`): per slot with `+0 != 0` (`0x5465`), `+1 != 0` (`0x54B9`), `+4 == g_floor` (`0x549A-0x54A2`), in view
  (`rel x, rel y <= 10`, `0x54A7-0x54B6`), terrain cell not `0xFF` (`0x54D4`) and not `0x87` (`0x54E7`):
  the classes `(+0 & 0xFC) == 0xE8`, `+0 == 0x1E`, `+0 == 0x1F` (`0x54F1-0x5501`) and a second test on the byte at +1 == 0x1D/0x1E (`0x554A-0x5552`) take a decal branch (the +1 byte is stored in the second plane `0xAC64`
  and the terrain-plane cell is zeroed, `0x5503-0x5546`, `0x5554-0x557F`); every other class goes to `call 0x51B8` (sprite draw with the +1 byte, `0x55E6-0x55FE`). So the bodies (`+0 = +1 = 0x1E`) draw via the decal branch, the skiff via the normal one.
  Slot 0 is written at the top of the same routine from the party (`0x53A6-0x53BF`), only when `g_location < 0x80`.
* Movement (`MAINOUT.OVL:0x01FE` step; `0x0236 call find_object_at_xy(x+dx, y+dy, g_floor)`): an object in the target cell makes the step blocked
  (`[bp-2] = 0`) unless (transport < 0x20 or >= 0x30, i.e. foot/horse/carpet) the object byte is in `[0x24,0x2C)` or equals `0x1B` or `& 0xFE == 0x10`, or
  (transport `0x28..0x2F`, skiff) the object byte is in `[0x24,0x28)`; transports `0x20..0x27` are always blocked by an object. THEN the terrain must still pass
  `0x2C4C(transport, terrain tile)` (`0x02A1-0x02B9`), whose foot class is the walkability bitmap `DS 0x54D4` (`0x2BD4`).
  Consequences read from code: a foot party is blocked by a 0x1E body (0x1E < 0x24, != 0x1B, `& 0xFE` = 0x1E); the skiff byte 0x29 passes the object test for a foot
  party but its cell terrain must also be foot-walkable. The binary bitmap says terrain 0x03 (WaterCoast, the seed skiff cell (14,242)) is BLOCKED for foot
  (`d82c` check: bitmap bit set; the neighbour (14,243) is 0x30 OutsidePath1, walkable). TileData.json agrees with the bitmap on 247/256 tiles incl. these.
* Board (`CMDS.OVL:0x07F6`): `0x0826 call find_object_at_xy(g_x, g_y, g_floor)` = the party's OWN cell; `(byte & 0xFC) == 0x28` -> `0x08A1`: boarding gate `0x06EE` (the party must be on foot: `[0x587C]` = 0x1C or 0x1D, `0x06EE-0x06F8`),
  "skiff\n" (DS 0x4275), `[0x587C] = byte`, then the common tail `0x093E`: six zeros then the slot pushed, `0x0949 call 0x3A74`, frees the record. The skiff branch does NOT touch
  `g_hull`/`g_skiffs` (only the frigate branch `0x08C4-0x0939` does).
* X-it (`CMDS.OVL:0x0EB4`, tail `0x0FF4`): allocates with `0x38E4`, writes the vehicle left behind with `call 0x3A74` pushed as (tile, tile, `[0x5896]`, `[0x5897]`, `[0x5895]`, `[0x5C5F]`, slot) `0x0FFA-0x1016`
  and then `[slot+7] = bp-8` (`0x1020-0x1023`) at the party's cell: a dropped skiff is a table record of exactly the seed's shape (the port models it as a terrain cell, see 4/5).
* Ship purchase (`MAINOUT.OVL:0x0D22`): the placed dock object is `tile = (flags > 0x7F) ? 0x25 : 0x29`, `+5 = 0x63`, `+7 = flags & 0x3F`, `+4 = 0` (so 0x29 is "a skiff-class
  object" for the purchase too).
