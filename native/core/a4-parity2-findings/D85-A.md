# D-85 (A) -- the location-29 trapdoor: binary-first report

Investigator lens: binary first. Everything in sections 1-3 was derived from `ULTIMA.EXE` / `TOWN.OVL` /
`DATA.OVL` / `KEEP.DAT` with `re/tools/dis16.py`-equivalent capstone disassembly (my wrapper
`scratchpad/findings/ovdis.py` adds near-call resolution) BEFORE any note or port was opened. Sections 4-6 are the
secondary comparison. Nothing inside the repository was modified.

Conventions: `TOWN 0xNNNN` = file offset in TOWN.OVL (base 0x81D0); `K 0xNNNN` = ULTIMA.EXE image offset
(MZ header skipped, equals CS:IP in the notes); `DS 0xNNNN` = data-segment offset (DATA.OVL file offset = DS + 0x10).
All Pascal-style calls: the first pushed argument is the first parameter, callee pops (`ret 2n`).

---------------------------------------------------------------------------------------------------------------

## 1. Verdict

1. **D-85 is confirmed exactly as described, and the loop bound is the party size.** The kill loop is
   TOWN 0x0ff9-0x103a. It is bounded by the BYTE at DS 0x585b (`mov al,[0x585b]`, zero-extended, `cmp [bp-4],ax /
   jb`), which is the **party size** (<= 6), NOT the roster (16 records of 0x20 bytes at DS 0x55a8-0x57a7).
   Indices touched: `0 .. [0x585b]-1`. Per touched member: the WORD at record+0x10 (HP) := 0, the BYTE at record+0x0b
   (status) := 0x44 ('D'). Nothing else in the record is written. Roster members at index >= [0x585b] (inn companions)
   are not touched. Dead ('D'), sleeping ('S') and poisoned ('P') members are not skipped (no status test in the loop).
2. **Trigger:** tile byte 0x8C (140) under the party, in **location 29 = KEEP.DAT slot 4 = "Stonegate"** (the only
   map of that location is KEEP.DAT record 6, level 0). The tile is NOT a single tile: it is the 8-cell ring
   (14,14)(15,14)(16,14)(14,15)(16,15)(14,16)(15,16)(16,16) around the safe centre (15,15)=0x44. It is checked after
   EVERY turn-consuming town command (post_turn TOWN 0x0f02, single caller TOWN 0x15ec), not only on arrival. Exempt:
   carpet (`[0x587c] & 0xfe == 0x14`). A horse (0x12/0x13) is NOT exempt.
3. **After the kill:** no game-over exit, no respawn code inside this routine. Control returns to the town command loop,
   housekeeping (K 0x2ae8) and the NPC tail run once, then the loop top (TOWN 0x1436) calls K 0x39fc which returns -1
   (no 'G'/'P'/'S' member) and TOWN 0x1862 runs the **Refuge** (kernel wrapper K 0x0e7c -> thunk K 0x7a5e -> BLCKTHRN.OVL
   0x0910 `party_refuge`). The Refuge is the same routine a combat wipe uses.
4. **RNG: the kill loop itself draws nothing from the main RNG (DS 0x5420).** Its noise bursts use the private LCG
   DS 0x545c.
5. **NEW FINDING that the implementer must know before touching this code (not D-85, but in the same branch):** both
   ports state "no RNG in the whole branch". The binary disagrees. Before the location-29 test at TOWN 0x0f96, EVERY
   trapdoor (all locations, including the non-29 falls) executes, between the message and the floor/kill branch,
   (a) TOWN 0x0f8a `call` K 0x5910 (viewport redraw + wind tick, with the party's transport tile `[0x587c]` zeroed
   around it) and (b) TOWN 0x0f8d `call` K 0x2aa8 = `party_random_damage`: `rand(1,8)` HP damage to every living
   party member. Neither port does either. Details in 2.6 and 5/6/7.
6. Both ports kill the whole roster (D-85 as reported) and additionally the native device audio plays one noise burst
   per ROSTER member. The confirmed binary behaviour is party-size everywhere.

## 2. Binary facts

### 2.0 Tooling controls (run before trusting anything)

* **Overlay near-call arithmetic:** a call with target `t` (as capstone prints, may be `0xffffXXXX`) resolves to kernel
  `(t + 0x81D0) & 0xFFFF` for TOWN. Controls: TOWN 0x0f2a `call 0xffff9ec2` -> K 0x2092 (prologue `55 8b ec`, the RNG
  `rand(lo,hi)`), TOWN 0x10a6 `call 0xffffa730` -> K 0x2900 (prologue), TOWN 0x0f8a `0xffffd740` -> K 0x5910 (prologue),
  TOWN 0x0f8d `0xffffa8d8` -> K 0x2aa8 (prologue), TOWN 0x101e `0xffffa06c` -> K 0x223c (prologue), TOWN 0x0fbb
  `0xffffa112` -> K 0x22e2, TOWN 0x0fc6 `0xffff9ef8` -> K 0x20c8, TOWN 0x0fd3 `0xffffa13e` -> K 0x230e (speaker off,
  `in al,0x61 / and al,0xfc / out`). All land on routine starts.
* `re/tools/callers_banda.py 2092` lists TOWN 0x0f2a and 0x108d, exactly the two RNG calls I read in post_turn: positive
  control OK.
* **String control:** DS 0x54c8 -> DATA.OVL file offset 0x54d8 = `Starving!\n`, which is what K 0x2b6d prints right
  after `mov ax,0x54c8`: the "+0x10" rule holds.
* **Correction to the task brief's base table:** BLCKTHRN.OVL's base is **0xA290**, not 0xE63E. Proof: with 0xA290, BLCKTHRN
  0x091c `call 0x828e` -> K 0x251e (prologue `55 8b ec c7 06 94 53`); with 0xE63E it lands on K 0x68cc, mid-instruction
  garbage. The overlay descriptor table at ULTIMA.EXE image 0x7780 (16-byte records, word +4 = size in paragraphs, word +0xA =
  load segment) lists overlays in the file-name order TOWN, MAINOUT, DUNGEON, INTRO, FLAMES, NPC, COMBAT, BLCKTHRN, ...
  (record 8 = size 0x00c7 paragraphs = 3184 B = BLCKTHRN.OVL, segment 0x0a29). Thunk overlay ids index that table:
  thunk id 8 = BLCKTHRN, so "ovl 19" in `thunks.py` is ZSTATS, not BLCKTHRN. (The thunk `ovlbase` column is only
  "lowest thunk target", not the load base.)
* TOWN.OVL local calls (`call 0x0408`) resolve to `(t+0x81D0)`, still inside the overlay.

### 2.1 What the party bytes are

* Record table: DS 0x55a8 + 0x20*i, 16 records (0x55a8 + 16*0x20 = 0x57a8 = the food word). Field offsets proven by the
  code itself: status = +0x0b (`[si+0x55b3]` with si = i<<5), HP word = +0x10 (`[si+0x55b8]`), location-of-stay byte = +0x1f
  (`[bx+0x55c7]`).
* **DS 0x585b = party size.** Evidence: (a) writers, found by exhaustive byte-pattern scan of every overlay and the EXE
  (`fe 06 5b 58` inc / `fe 0e 5b 58` dec / `a2 5b 58` / `c6 06 5b 58`): TALK.OVL 0x0912 `inc byte [0x585b]` straight after the
  join swap (TALK 0x08c8-0x0910: record copied to a stack temp, `[rec+0x1f] := 0`, then copied to index `[0x585b]`, i.e. the
  first slot past the party); SHOPPES3.OVL 0x083a `inc` (same swap pattern at 0x0820-0x0837); SHOPPES3.OVL 0x0472 `dec`
  after the leaving member's record is copied to roster slot 15 (`mov di,0x5788`, 0x0465) and `[bx+0x55c7] := [0x5893]` at
  0x040a-0x040f records the inn location; BLCKTHRN.OVL 0x04d4 `dec` (Blackthorn execution); (b) every party loop uses it as
  its bound and additionally caps at 6: K 0x2aa8 (`cmp si,6 / jl`, `cmp ax,[0x585b] / jae skip`), K 0x2726 (panel row: row
  index >= [0x585b] prints a blank row), K 0x39fc, K 0x2ae8.
* Therefore non-party roster members are exactly records `[0x585b] .. 15` (the inn companions); they carry their inn in +0x1f.

### 2.2 post_turn (TOWN 0x0f02) -- the whole routine, in order

```
0f02 push bp / mov bp,sp / sub sp,0xc / push di / push si
0f0a mov [bp-4],0
0f0f mov al,[0x585b] / sub ah,ah / or ax,ax / je 0xf48           ; party-size bound
0f18 mov si,0x55b3                                               ; status of member 0
0f1e cmp byte [si],0x53 ('S')      jne 0xf35
0f23 push 0 ; push 0xf ; call K 0x2092   -> rand(0,15)           ; ONE draw per sleeping member, index order
0f2d cmp ax,0xf / jne 0xf35 / mov byte [si],0x47 ('G')           ; wakes only on 15 (1/16)
0f35 add si,0x20 / inc di / cmp di,[0x585b] / jb 0xf1e
0f48 mov [bp-2],0                                                ; "fell" flag
0f4d mov al,[0x5896] / push ax ; mov al,[0x5897] / push ax       ; (x , y) -- see 2.3
0f57 call K 0x4402 (tile_ptr)  ; mov bx,ax ; mov al,[bx] ; sub ah,ah ; mov [bp-8],ax
0f63 cmp ax,0x8c / je 0xf6b / jmp 0x1050                          ; TRAPDOOR TEST
0f6b mov al,[0x587c] / and al,0xfe / cmp al,0x14 / jne 0xf77 / jmp 0x1050   ; carpet (0x14,0x15) skips
0f77 mov ax,0x2768 / push ax / call K 0x1850                      ; print DS 0x2768 = "A TRAPDOOR!\n"
0f7e mov al,[0x587c] / sub ah,ah / mov [bp-6],ax                  ; save transport tile
0f86 mov [0x587c],ah                                              ; ah==0 -> transport tile := 0
0f8a call K 0x5910                                                ; viewport redraw + wind tick   (see 2.6)
0f8d call K 0x2aa8                                                ; party_random_damage           (see 2.6)
0f90 mov al,[bp-6] / mov [0x587c],al                              ; restore
0f96 cmp byte [0x5893],0x1d / je 0xfa0 / jmp 0x103c               ; LOCATION 29 ?
```
`0x1d` = 29. `[0x5893]` = current location (also used by TOWN 0x0408 as the file/record selector).

### 2.3 Coordinates and tile id

K 0x4402 `tile_ptr(a=[bp+6], b=[bp+4])` for 1 <= location <= 0x7f returns `0x6608 + (b<<5) + a` (K 0x447e-0x44a8; negative
or > 0x1f arguments return the constant 0x6a07 instead). The call at TOWN 0x0f4d pushes `[0x5896]` first (= a, the
column) and `[0x5897]` second (= b, the row). So **[0x5896] = x, [0x5897] = y**, the tile is the raw map byte at
DS 0x6608 + y*32 + x, compared as a byte widened to a word with 0x8c (`3d 8c 00`, TOWN 0xf63).
This is the ONLY `cmp ax,0x8c` in TOWN.OVL.

### 2.4 The location-29 branch: TOWN 0x0fa0-0x10c7 (exact)

```
0fa0 sub ax,ax / push ax / call K 0x0a70      ; set_color(0): [0x52da] := 0 & mask, lcall [0x5350]=0x2d
0fa6 mov ax,8 / push ax / push ax / mov ax,0xb7 / push ax / push ax / call K 0x0aa6
                                              ; fill_rect(8,8,0xb7,0xb7) = the 11x11 tile viewport (176 px), colour 0 -> BLACK
0fb3 mov [bp-4],0x3e8
0fb8   push [bp-4] / call K 0x22e2            ; set_tone(freq = [bp-4])  (PIT: 0x1234de / freq)
0fbe   push 1 / mov ax,0x28 / push ax / call K 0x20c8   ; delay(1, 0x28)  (busy-wait, calibrated by [0x5356])
0fc9   dec [bp-4] / cmp [bp-4],0xfa / jg 0xfb8          ; signed: 1000 .. 251  => 750 iterations
0fd3 call K 0x230e                            ; speaker off
0fd6 mov cx,0x400 / mov di,0x6608 / mov ax,ds / mov es,ax / mov ax,0x8f / repne stosb
                                              ; the WHOLE 32x32 local map := tile 0x8F (143, "Lava")
0fe5 mov byte [0x24e6],1                      ; full viewport redraw requested
0fea mov cx,0x100 / mov di,0x5c5a / ... sub ax,ax / repne stosb   ; DS 0x5c5a..0x5d59 := 0 (32 x 8-byte actor/object slots)
0ff6 mov [bp-4],ax                            ; index := 0 (ax is 0 here)
0ff9 mov al,[0x585b] / sub ah,ah / or ax,ax / jne 0x1005 / jmp 0x10c7    ; PARTY SIZE ZERO -> skip
1005 mov si,0x55b8 / mov di,0x55b3            ; HP word of member 0 / status byte of member 0
100b mov word [si],0                          ; HP := 0
100f mov byte [di],0x44                       ; status := 'D'
1012 mov ax,0x28 / push / mov ax,0xbb8 / push / mov ax,0x1f4 / push / call K 0x223c   ; noise_burst(0x28, 3000, 500)
1021 call K 0x2900                            ; redraw the stat panel
1024 add si,0x20 / add di,0x20
102a inc word [bp-4]
102d mov al,[0x585b] / sub ah,ah / cmp [bp-4],ax / jb 0x103a   ; unsigned: index < party size -> loop
1037 jmp 0x10c7                               ; (0x103a: jmp 0x100b = the back edge)
```
* Bound variable: `[0x585b]` re-read from memory every iteration (byte, zero-extended, unsigned compare). Body executes
  before the first compare but the pre-check at 0x0ff9 skips an empty party.
* Touched: `[0x55b8 + 0x20*i]` (word 0) and `[0x55b3 + 0x20*i]` (byte 0x44) for `i = 0 .. party_size-1`. No filter on
  current status; a member already 'D' is rewritten identically (and still gets a burst and a panel redraw).
* **[0x587b] (active character) is not touched in this loop.** K 0x2ae8 (housekeeping, called next) resets `[0x587b] := 0xff`
  when `status[i]=='D' && i == [0x587b]` (K 0x2b14-0x2b25).
* End: `0x10c7 cmp [bp-2],0 / je 0x10d0` -> `0x10d0 call K 0x2ae8` (housekeeping) -> `ret`. `[bp-2]` stays 0 on the
  location-29 path, so the loop does NOT re-enter 0x0f48 (unlike the non-29 fall).

### 2.5 The other branch (any location != 29), for the boundary tests

```
103c dec byte [0x5895]                 ; floor/level byte: 0 -> 0xFF (z=-1), no bounds check
1040 push 1 / call 0x0408              ; TOWN local-map loader, arg 1 = reposition (NPC schedule)
1047 mov [bp-2],1                      ; -> 10c7: jne -> jmp 0xf48 : re-read the tile on the new floor
```
The re-entry at 0xf48 skips the wake loop (0xf0a-0xf45) but repeats the whole trapdoor block, including 0x0f8a/0x0f8d.
Housekeeping 0x10d0 runs once.

* No other text is printed in the kill path. The Refuge prints its own lines (BLCKTHRN).
* **Timing is calibrated, not fixed.** `delay(sel,n)` K 0x20c8: `[0x5422] := [0x5356] >> word[0x5426+sel]; [0x5424] := n;
  repeat n times: dec [0x5422] until 0`. `sel` is used unscaled as a byte index into the DS image bytes
  `00 00 00 00 01 00 01 00 02 00 02 00`, so `sel=1` reads the word `0x0000` (no shift) -- an image value, if the table
  is rewritten at runtime that changes. `[0x5356]` (K 0x11b4-0x120b) = (iterations of `inc [0x5356]; cmp [0x535a],0; je`
  counted during one INT 1Ch tick, 54.9 ms) * 0x12 / 0x2ee, i.e. N * 0.024, the number of delay-loop iterations that the
  calibration maps to ~1.3 ms of calibration-loop time. So step 6 is 750 * 40 * ~1.3 ms ~ 40 s in calibration-loop units; the
  `dec mem / jne` loop is cheaper per iteration than the calibration loop, so real time is shorter (the audio track measures
  ~28 s; I did not run the original). Not exactly determinable from the bytes alone.
* noise_burst K 0x223c(a,b,c): speaker on; loop { freq := 100 + LCG[0x545c] % (c-100+1); PIT := 0x1234de/freq;

  K 0x2092 callers shows none inside K 0x223c, K 0x2900, K 0x2726, K 0x2a28, K 0x230e, K 0x22e2, K 0x20c8 (so the kill loop
  cannot draw).
* SFX: falling ramp (step 6), one burst per party member (step 10), fall-damage bursts (step 3).

### 2.8 Which location is 29, and which tile

* TOWN 0x0408 loader: file = DS word table at 0x2652 indexed by `(loc-1)>>3` = {0x2626 "TOWNE.DAT", 0x2630 "DWELLING.DAT",
  0x263d "CASTLE.DAT", 0x2648 "KEEP.DAT"}; record = `byte[DS 0x1e19 + loc] + signed(level)`, offset `record << 10`,
  size 0x400 into DS 0x6608. Loc 29: (29-1)>>3 = 3 -> KEEP.DAT, `[0x1e19+29] = 6`, next location's base = 7, so loc 29 has ONE map.
  KEEP.DAT slot 4 (0-based) = Stonegate (the device's `location_display_name` table, native/targets/tdeck/main/location_names.h:19,
  also puts "Stonegate" at index 29: consistent; the binary itself holds no location-name table).
* KEEP.DAT record 6 (file 0x1800-0x1bff): tile 0x8C appears only at (14,14)(15,14)(16,14)(14,15)(16,15)(14,16)(15,16)(16,16);
  (15,15)=0x44. Other maps with 0x8C (for orientation): Yew record 7 (20,1),(25,8); Palace of Blackthorn records 6-9 (many); Serpent's Hold
  record 14 (13,4). Tile 0x8F ("Lava") appears naturally in Lord British's castle record 5 (not relevant).

### 2.9 Can it fire with a dead or sleeping member?

Yes. post_turn has no party-state precondition on the trapdoor test. The sleeping wake rolls run first, one draw per 'S'
member. Dead and sleeping members are rewritten like everyone else. The only precondition for the whole town turn is
the dispatcher reaching TOWN 0x15ec (after the command handler returned non-zero and K 0x39fc at 0x15bf did not
return -1).

### 7.2 Separate finding (needs an owner decision; I recommend a new D number)

In both `townTurn` / `town_turn`, in the trapdoor branch, after the message and BEFORE `onTrapdoor`:
`if (time_spell != 'T') { wind tick (maybeChangeWind) }` then `partyRandomDamage` (rand(1,8) per non-'D' party member, existing helper).

exactly as it covers the Burning damage; the kill itself stays outside God Mode (ALPHA4_UI.md:2605).

### 7.3 Boundary tests (D-85)

1. roster 5, party 2, all 'G': after the 29 trapdoor chars 0,1 = HP 0/'D'; chars 2-4 byte-identical (HP, status, every field).
2. roster 16, party 6 (maximum): 0-5 dead, 6-15 untouched. Roster == party == 6: all dead.

4. Pre-existing statuses inside the party: 'D', 'S', 'P' members all end HP 0 / 'D'; a non-party 'S'/'P' member is not touched. Sleeping members draw
   `rand(0,15)` BEFORE the tile read (index order); non-party sleepers draw nothing (wake loop bound is also the party size).
