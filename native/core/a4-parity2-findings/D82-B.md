## 1. Verdict

**The derivation can be finished, and it is finished: the original read path, the record layout, the world
lifecycle and the live-table representation of all five objects are established from the binary.**
What is NOT closed is listed in section 8 (small, all stated with the evidence that would settle them).

One-paragraph answer:

* INIT.OOL is a raw **256-byte image of the live object table (DS:0x5C5A, 32 records x 8 B)**, and it seeds
  the **UNDER block only**. It is read at **two** sites (new game `FONT.OVL:0x0df6`, and the U4-transfer
  new-game path `INTRO.OVL:0x1372`), both into DS:0xB31E, and written verbatim as the second half of a fresh
  512-byte `SAVED.OOL` whose first half (BRIT block) is 256 zero bytes (`FONT.OVL:0x0e11-0x0e2b`).
  Journey Onward (`INTRO.OVL:0x0f26-0x0f89`) splits `SAVED.OOL` into `BRIT.OOL`/`UNDER.OOL`; the five
  records reach the live table the first time the party enters the Underworld through a path that
  **reads UNDER.OOL into DS:0x5C5A** (the Falls, `OUTSUBS.OVL:0x0538`; a moongate buried in the Underworld,
  `ULTIMA.EXE:0x4898`; or the kernel reload after leaving a town/dungeon, `ULTIMA.EXE:0x013c`). The read is
  raw (no transformation): **all 32 records are copied, including slot 0**, which resets g_hull/g_skiffs.
* The **whirlpool** (`MAINOUT.OVL:0x126e-0x12c1`) is the one entry that never swaps the table, so a
  whirlpool-first entry leaves the Britannia table live under `g_floor=0xFF`, and the next park overwrites
  UNDER.OOL (the seeds are lost in the original in that sequence). Static result, no runtime witness.
* In the live table the skiff is record `29 29 0e f2 ff 00 00 00` (slot 23, DS:0x5D12) and the corpses are
  `1e 1e xx yy ff 00 00 00` (slots 24-27, DS:0x5D1A..0x5D32). Objects vs monsters are split by tile class
  (`MAINOUT.OVL:0x105c`), objects are floor-gated (`+4 == g_floor`), drawn as sprites replacing the terrain
  cell, **corpses block walking, the skiff can be walked onto and boarded, neither can be picked up**.
  They survive saves (live table inside `SAVED.GAM`+0x6B4, parked copy in the matching `SAVED.OOL` block).
* Faithful representation vs A4-SAVE3: the skiff as a **terrain cell** (what the PC bridge already does,
  `0:255:14:242 = 0x129`) is the correct port channel for it, and **must not** be a `ship` object in either
  port (two real hazards in section 4/5: board() copies the object's hull/skiffs onto the party; both JSON
  codecs write ship objects into the live table floor-blind). The four corpses have no channel in the bridge
  today; the `prop` object (the interior-dead-body representation both ports already use) is the match.
* Corrections to the brief: the overlay-base table in the task text is wrong for 10 of the overlays it lists
  (OUTSUBS, COMSUBS, SHOPPES3, LOOKOBJ, DNGLOOK, CAST, COMBAT, INTRO, DUNGEON, BLCKTHRN) and `re/tools/callers_banda.py`
  `BASES` is wrong for 13 of its 20 overlay entries (appendix A). With the shipped tool the census of the file writer finds 4 of 17
  call sites.

Confidence: **high** for the binary mechanics (everything is anchored by at least two independent
instruction-level facts), **medium** for the whirlpool consequence and the hull-reset side effect (static
only), **high** for the port status.

## 2. Binary facts

Notation: `OVL:off` = file offset in the overlay (the disasm address); `K:addr` = ULTIMA.EXE image offset (MZ
header 0x800 skipped); `DS x` = DATA.OVL offset x (file offset = x + 0x10). Calling convention of the kernel
file helpers is Pascal (callee pops): `K:0x256e read(name, buf, count, offset)` (`ret 8`) and
`K:0x25d8 write_whole(name, buf, count)` (`ret 6`); they wrap `K:0x7234`
(`int 21h/3Dh open mode 2, 42h lseek from start (skipped when offset==0), 3Fh read (count 0 => 0xFFFF), 3Eh`) and
`K:0x7296` (`3Ch create (truncates), 40h write, 3Eh`). So a ".OOL read" is "open, read N bytes at offset 0".

History.txt: INTRO/FONT/MAINOUT/TOWN/DUNGEON/ENDGAME.OVL and the DATA.OVL patch are the 2001 music-patched
versions; OVL mtimes Aug 2001). No pristine 1988 ULTIMA.EXE is in the tree, so nothing here can be diffed
against the 1988 build; the save/world paths I read are not touched by the MIDI patch as far as the note

### 2.1 The files

  `[+3 y][+4 floor][+5 hull/aux][+6 mover state][+7 skiffs/aux]` (same record the `K:0x3a74` writer fills:
  `mov [si+0x5c5a..0x5c5f]` from args at `[bp+0x10 .. +6]`, `ret 0xe`).
* INIT.OOL, byte-exact (hex pairs per record, slot : file offset):
  `23 : +0xb8  29 29 0e f2 ff 00 00 00`  skiff, x=14, y=242, floor 0xFF
  `24 : +0xc0  1e 1e 67 e2 ff 00 00 00`  corpse (103,226)
  `25 : +0xc8  1e 1e 69 e3 ff 00 00 00`  corpse (105,227)
  `26 : +0xd0  1e 1e 6b e3 ff 00 00 00`  corpse (107,227)
  `27 : +0xd8  1e 1e 6c e1 ff 00 00 00`  corpse (108,225)
  Live DS addresses: slot s = `0x5C5A + 8s`: 0x5D12, 0x5D1A, 0x5D22, 0x5D2A, 0x5D32. The Amulet is at (105,225).
* **BRIT.OOL/UNDER.OOL are not distribution data**: they are DOSBox scratch written by Journey Onward

### 2.4 The kernel main loop: reload after every town/dungeon (`ULTIMA.EXE:0x00b8-0x017d`)
```
00b8 [bp-2]=0
00bd cmp byte [0x5893],0 ; jne 00d1 ; 00c4 call 0x7a3a (-> MAINOUT.OVL:0x0d22)   ; outdoor run if g_location==0
00db cmp byte [0x5893],0x21 ; jae 0104  (dungeon: 0x7a16)  else town: 0x7a46 / 0x7a52
0116 [bp-2]=0 ; K:0x251e(1) ; wait BRIT.DAT (DS 0x1393, K:0x1674)
012d call 0x7a22 (world_filename)     ; push ax ; push 0x5c5a ; push 0x100 ; push 0
013c call K:0x256e                    ; read(world_filename(g_floor), 0x5C5A, 0x100, 0)   <-- UNCONDITIONAL
013f cmp byte [0x5893],0 ; jne 016e ; 0146 cmp byte [0x5895],0 ; je 016e    ; outdoors & g_floor!=0:
014d K:0x251e(5); wait UNDER.DAT (DS 0x139c); 015f call 0x7a22 ; ... 016b call K:0x25d8   ; mirror write
016e cmp word [bp-2],0 ; jne 0177 ; jmp 00b8
```
`world_filename` is `OUTSUBS.OVL:0x0368` (thunk `K:0x7a22` -> `0xa5f8 = 0xa290+0x368`):
`036e 80 3e 95 58 00 cmp byte [0x5895],0 / 75 07 jne 037c / c7 46 fe 89 39 mov word[bp-2],0x3989 ("BRIT.OOL")
/ eb 05 / 037c c7 46 fe 92 39 mov word[bp-2],0x3992 ("UNDER.OOL")`. **Selector: `g_floor == 0` -> BRIT, any
nonzero -> UNDER** (byte compare, equality, no signedness). The first outdoor run after a load does NOT go
through the reload: a game saved outdoors resumes with the table from SAVED.GAM.

Facts that follow (all derived above):
1. **Live vs parked.** The table of the world the party is in is in `SAVED.GAM`; the other world's table is
   in `SAVED.OOL`. The `.OOL` block of the ACTIVE world is stale (it is only refreshed when that world is
   parked), and a save never refreshes it. On load nothing reads it until the next park overwrites it.
2. Which world's `.OOL` is addressed is decided by `g_floor` at the moment of the call (`==0` BRIT,
   else UNDER), except the Falls which hard-wires names. `g_floor` inside a dungeon is the dungeon level
   (0..7), so `world_filename()` is only meaningful outdoors / at a park from the surface.
3. **Table copy semantics: raw 256 bytes both ways. No filtering, no record translation.** The read overwrites
   slot 0, whose bytes are the party/vehicle record **and the globals g_hull (`[0x5c5f]`, CMDS:0x08f4 / MAINOUT
   0x10be) and g_skiffs (`[0x5c61]`, CMDS:0x0936 / MAINOUT 0x10dd)**. UNDER.OOL slot 0 is zero in a new game,
   so the first Underworld load sets g_hull = g_skiffs = 0 (nothing in OUTSUBS:0x0458-0x055f or K:0x47f4
   restores them; only `[0x587c]` is saved/restored around the Falls animation, `0x0495/0x04fa`). The painter
   re-mirrors only `+0..+4` of slot 0 each frame (`K:0x53a6-0x53be`).
4. Seeds become live **only through a load site**: Falls, a moongate buried in the Underworld, or a kernel
   reload with `g_floor!=0` (i.e. after a visit to a town/dungeon entered from the Underworld, or an exit with
   `g_location==0x19`/underworld-dungeon exit). In a new game the Falls (a waterfall pull that leaves the party exactly on `(0x36,0x8a)`, `OUTSUBS:0x0500-0x050c`) and the
   whirlpool are the realistic first entries (every moonstone starts with location 0 / floor 0: INIT.GAM
   0x29a..0x2a9).
5. **Whirlpool-first quirk:** after `0x12c1` the table in DS 0x5C5A is still Britannia's (floor byte +4 == 0)
   while `g_floor==0xFF`; the painter (`K:0x54a0 cmp [floor byte], g_floor`) and `find_object_at_xy` therefore
   show no Britannia object, and the first park (`world_filename()` -> UNDER.OOL, e.g. entering a dungeon,
   `MAINOUT:0x0857`, or a moongate with `old==0`) overwrites UNDER.OOL with that table: the five seeds are
   destroyed. (BRIT.OOL keeps the last Britannia park.) Static derivation only.

### 2.6 What happens to the table right after a load: `seed_underworld_plot`
`MAINOUT.OVL:0x0000-0x0079` (`outdoor_mode_init`, ends `0x0076 call K:0x7b96`) is the only caller of
`OUTSUBS.OVL:0x0566` (stub 0x7b96 -> 0xa7f6). It runs after every table load above (Falls, moongate,
`K:0x00c4 -> MAINOUT:0x0d22 -> call 0`). The routine (`0x056e cmp byte [0x5895],0 ; je 05e8`, i.e. **g_floor !=
0**, not `==0xFF`) writes with no occupancy check:
```
0575 cmp [0x57b3],0 ; jne 059d     ; amulet flag (GAM+0x20d) == 0
057c..0598  [0x5d3b]=[0x5d3a]=0xb7 ; [0x5d3c]=0x69 ; [0x5d3d]=0xe1 ; [0x5d3e]=0xff ; [0x5d3f]=0xf3   -> slot 28
059f..05e0  for i=0..2: if [0x57b6+i]==0 (shard not taken) && [0x58c8+i] < 0x80 (Shadowlord alive):
            rec = 0x5d42 + 8i = slots 29,30,31 : +0=+1=0xb4, +2=[0x3a06+i], +3=[0x3a0a+i], +4=0xff, +5=[0x3a0e+i]
```
It writes `+0..+5` only (not +6/+7). It does not touch slots 23-27. Slots 28-31 of the Underworld table are
therefore **rewritten on every Underworld load whenever the matching plot item is untaken** (all four in a new
game: INIT.GAM +0x20d=0, +0x210..0x212=0, +0x322..0x324=0): a vehicle/object parked in 28-31 is destroyed.

### 2.7 Representation, class split, floor semantics
* `K:0x368e find_object_at_xy(x, y, floor)` (Pascal, `ret 6`): scans slots **1..31** (`di=0x5c64` = slot 1 +2;
  loop ends `cmp si,0x5d5a`), matches `+2==x`, `+3==y` and `+4 == floor` (zero-extended byte vs word arg; the
  floor test is skipped when `g_location > 0x7f`), returns `+0` and stores the slot in `[0x5876]`. It does not
  look at the tile class and does not test `tile != 0`.
* `K:0x3702` is the descending (31->1) twin. Callers in the section 3 census.
* Object vs monster: `MAINOUT.OVL:0x105c is_monster_tile(tile)` (`ret 2`): returns 1 for `0x2c..0x2f`, 0 for
  `< 0x80`, 0 for `0xb4..0xb7` and `0xe8..0xeb`, 1 for everything else `>= 0x80`. The world turn
  (`MAINOUT:0x1a60`, slots 31->1: `0x1ac1 call 0x105c ; je skip`) only moves/despawns monsters
  (despawn `0x1b1f K:0x3a74(slot, 0,0,0,0,0,0)` only when `(byte)(x-[0x589b]) > 0x1f` or `(byte)(y-[0x589c]) > 0x1f`, unsigned: `0x1b01 sub al,[0x589b] ; cmp al,0x1f ; ja`). **Tile 0x29 and 0x1e are
  objects: never moved, never despawned.**
* Pool: the spawn/recycle allocator `K:0x3868` scans **slots 1..23** (`0x3870 mov cx,1 ... 0x38cf cmp cx,0x18
  / jl`), range `lo<=tile<=hi`, tile 0xb5 excluded; `K:0x38e4` calls it ten times (free (0,0); (1,0xf) near;
  (0x80,0xff) near; (0x10,0x11) near; (0x30,0x7f) near; then the same four far; last resort (0,0xff) far).

  `CAST2 0x04aa`, each followed by the blitter `K:0x56ac`): when `g_location < 0x80` it first mirrors the party
  into slot 0 (`0x53a6-0x53be`: +2=[0x5896], +3=[0x5897], +4=[0x5895], +0=+1=[0x587c]), then walks slots
  31->1 (`0x5462`..`0x5636`). A record is skipped if `+0 == 0` (`0x5465`) or `+1 == 0` (`0x54bc`); when
  `g_location < 0x80` it must have `+4 == g_floor` (`0x549a-0x54a0`, byte compare) and lie in the 11x11 window
  (`(byte)(x-([0x5896]-5)) <= 10` and the same for y: `0x548a-0x54b4`, `jbe`); it is also skipped if the terrain
  buffer cell holds 0xFF or 0x87 (`0x54d4`, `0x54e7`). Special classes (`0x54f1-0x5546`):
  `(+0 & 0xfc)==0xe8 || +0==0x1e || +0==0x1f` draw `+1` into the sprite layer (`[bx-0x539c]`, 16-wide rows) and
  set the terrain cell (`[bx-0x54fe]`, 32-wide rows) to 0 (skipped if the cell is already 0); other classes go
  through `K:0x51b8` which ends the same way (`0x5370-0x5388`: sprite layer = tile, terrain cell = 0).
  So both seeds are drawn **as sprites replacing the terrain cell**, using the **+1 byte** (0x29, 0x1e) as the
  tile; the sprite bank for byte b is `0x100+b` (0x129 SkiffRight, 0x11e DeadBody in `TileData.json`).
* Movement (`MAINOUT.OVL:0x01fe`, `ret 4`, called from the move handler 0x0490 at 0x0514): `find_object_at_xy`
  on the target; **any** object blocks ("Blocked!" `0x0322`, DS 0x29ae) unless the class table opens it:
  transport tile >=0x30 or <0x20 (foot, horse, carpet): object `0x24..0x2b`, `0x1b` or `(t&0xfe)==0x10`

  **corpse (0x1e) blocks the party; skiff (0x29) is enterable on foot/horse/carpet.** Monsters may not enter
  an object cell either (`MAINOUT:0x1482` second guard calls `K:0x3702`). The terrain-0 passability value is
  not derived (section 8).
* (B)oard (`CMDS.OVL:0x07f6`): `0x0826 call K:0x368e(party x, y, g_floor)`; `0x0832 and al,0xfe; cmp 0x10`
  horse, `0x087c cmp 0x1b` carpet, `0x0898 and al,0xfc; cmp 0x28` **skiff**, `0x08b8 and al,0xfc; cmp 0x24`
  frigate. Skiff branch `0x08a1-0x08b5`: gate `0x06ee` (g_transport_tile must be 0x1c/0x1d, else "On foot"),
  prints "skiff" (DS 0x4275), `g_transport_tile=[bp-0xa]` (the object's byte, facing preserved, **no +2**),
  jumps to the epilogue `0x093e`: `K:0x3a74(slot, 0,0,0,0,0)` clears the record, `or [0x24e6],2`.
  **Only the frigate branch (0x08d5-0x0939) copies the object's +5/+7 into g_hull (0x5c5f)/g_skiffs (0x5c61).**
* (G)et (`SJOG.OVL:0x18ce`, scan `0x1933-0x19bd`): accepts an object only if `+0 < 0x10` (loot category),
  `==0x19` (strange rock), `==0x1b` (carpet) or `(+0&0xfc)==0xb4` (plot items). **0x1e and 0x29 are skipped:
  neither the corpse nor the skiff can be picked up.**
* (L)ook (`LOOKOBJ.OVL:0x0990-0x0a98`, `0x09de call K:0x368e`; object found -> `0x06a4(tile)`): "Thou dost see"

* Removal paths I read: boarding (`CMDS:0x093e`), cannon (`CMDS:0x0a92`, behind `K:0x7bde` = `MAINOUT:0x105c`,
  monsters only), despawn (monsters only). None removes a 0x1e record. The remaining `K:0x3a74` writers are

### 2.8 The by-product facts that bear on the ports
* `UNDER.OOL` as parked is also where plot items are written back (they are re-seeded at the next load, 2.6).
* Reading a parked table does not run any "fresh" hydrate: seeds are persistent state. A skiff boarded in one
  session is gone in all later loads of that save; it can be re-created only by (X)-it parking
  (`CMDS:0x0ff4-0x1023`, slot from `K:0x38e4`).
* The Underworld table therefore starts with 9 live objects in the top slots: 23 skiff, 24-27 corpses, 28
  Amulet, 29-31 shards (if untaken and alive).

## 7. Proposed fix and boundary tests

Reference first (the TS layer pins the split; native follows byte for byte):

1. **Extractor**: derive `init.ool` as `zeros(256) ++ INIT.OOL` from the shipped `INIT.OOL`
   (size check == 256) instead of `BRIT.OOL ++ UNDER.OOL`; keep BRIT/UNDER.OOL unused (they are scratch).
   Add one pure classifier `seedsFromInitOol(init.ool)` -> `{ vehicles[], props[] }`: tile class
   frigate/skiff/horse/carpet -> vehicle channel; `0x1e/0x1f` -> prop; anything else -> reported, not guessed.
2. **Data path**: new optional fields on `ExtractedInitialState` (`worldObjects`, `mapOverrides`) or a small
   asset consumed by `createNewGame` (`state.ts:526`); absent -> no seeds (visitors with an older extraction
   keep working). Seeds are NEW-GAME state, never re-hydrated (the binary never re-seeds them).
3. **Representation (decision for the lead, recommendation given):**
   * skiff -> **terrain override** `0:255:14:242 = 0x129` (same channel as a dismounted skiff and as the PC
     bridge): no hull overwrite, no floor-blind export, nothing in `writeNativeWorldObjects`. Cost: it does not
     occupy pool slot 23 (spawn pool +1 vs the original, only observable in the Underworld with 22 monsters).
     If the lead prefers an object record, `Game.board()`/`commands.cpp:1026` must first gate the hull/skiffs
     copy on `isFrigate(tile)` (what `CMDS:0x08d5-0x0939` does) and the two JSON codecs must filter by the
     object's own floor.
   * corpses -> `prop` objects, `location 0, floor 0xFF, tile 0x11e`, `slot 24..27` (the interior corpse
     representation; render+block via `tileAt`; (L)ook "a corpse").
4. **PC bridge parity** (reference reader + native `pc_save.cpp`): read non-vehicle `0x1e/0x1f` records of both
   tables (live table when the party is outdoors in that world, else the parked block) on import; on export
   clear and rewrite them exactly like vehicles (otherwise the template's corpses come back twice); **do not
   place any exported record in slots 28-31 of the UNDER block** (and not in the live table while the party is
   in the Underworld) because `seed_underworld_plot` rewrites them on every load while the item is untaken.
5. Separate follow-ups (not D-82, listed so nobody conflates them): floor-blind `writeNativeWorldObjects`/
   `object_table`; `readNativeWorldObjects` classifying skiffs as `ship`; g_hull/g_skiffs reset by the
   slot-0 read on the first Underworld load; whirlpool-first loss of the seeds (decide: deliberate
   divergence, since the ports have no single swapped table); town 0x19 exit floor.

Boundary tests (names are suggestions; all are RED against today's code unless marked control):

  scratch files (different content) -> seeds unchanged (kills the provenance defect). Control: a test whose

* T3 skiff boarding: from foot at (14,242) `board()` -> message "skiff", transport 0x29, **`shipHull`/`shipSkiffs`
  unchanged** (set non-zero sentinels first), the cell reverts to terrain 3, a second `board()` -> "What?";

* T4 corpse: walking into any corpse cell is "Blocked!" on foot, on horse, in a skiff; `(G)et` from the adjacent
